P0
How to use this document
Work top to bottom within a phase. Never start a task whose dependencies are unmet. Never mark a task done without its acceptance check passing.
Task anatomy
Every task carries an ID, an owner badge — Agent means a coding model may do it, You means it requires a human and must not be delegated — a dependency line, the work itself with exact file locations, and a green acceptance check. The check is the definition of done. If it does not pass, the task is not done, and weakening the check to make it pass is a stop condition.
The nine rules
1. Failing test first. Where a task says to prove a defect before fixing it, that ordering is mandatory. A fix with no prior failing test has no evidence it fixed anything, and the evidence is unrecoverable once the fix lands.
2. Never invent a convention. If this document does not say how something is done, find an existing example in the codebase and copy it. Part 2 lists the four places where the obvious approach is wrong here.
3. Never git add -A or git add . Stage explicit paths, always excluding .claude-home/** and .claude/settings.local.json.
4. No secret values anywhere — not in commits, tests, evidence, screenshots or logs. Record rule ID, file and status only.
5. Deleting is the fix, not flagging. For code whose only implementation is fake, a feature flag around it is not containment.
6. Never edit an applied migration. Add a forward migration.
7. Outside the explicitly mandated containment and correctness fixes, no feature work may change existing behaviour for a merchant who has not opted into that feature.
8. Stop on any stop condition (P8.3). Leave payment initiation disabled, preserve evidence, escalate. Do not mark a phase complete because time ran out — record it incomplete with the exact blocker.
9. Local truth and external truth commit separately but cannot be lost between them. Any integration write uses a transactional outbox, a stable local operation identity, a persisted provider idempotency-key epoch, a leased worker and read-after-ambiguous-response recovery. Reuse the same provider key only while the provider documents it as live. After expiry, reconcile first; only a proved zero match may atomically close that epoch and create a new provider key for the same local operation. A process-local cron, a log table, a fresh UUID on every retry or reuse of an expired provider key is not durability.
Things an agent must never do in this project
* Rotate production secrets, alter Replit Secrets, or create/delete Neon branches.
* Apply production migrations, or deploy without the named human approval.
* Rewrite Git history, delete retained financial data, or contact customers.
* Call live Windcave, or enable any capability flag in staging or production.
* Resolve a product, legal or provider decision by guessing. Build fail-closed scaffolding and tests while the feature stays disabled instead.
P1
The map and sequence
Three workstreams. Their code-delivery lanes are gated rather than fully parallel — remediation gates the other two for a specific reason, while the explicitly named human discovery tasks may overlap.
Why Xero cannot go first
Xero sync writes a merchant's revenue into their real, GST-filed accounting ledger. The app can currently mark a payment successful without any provider ever being called — an unauthenticated request to /api/payments/apple-pay/process returns fabricated success whenever Windcave credentials are absent. Connecting Xero on top of that would propagate invented revenue into a tax return. The remediation plan's own feature freeze says the same thing in policy terms; this is the reason behind it.

Four places the plans collide
1. Apple Pay was wrongly rated done. An earlier assessment marked the wallet buttons compliant — true of the buttons, but it never examined the routes behind them. routes.ts:6203 and :6266 have no auth middleware and fabricate success. Correct rating is blocking, and it belongs to R0 rather than the Apple track.
2. Tap to Pay's open question is answered. src/plugins/TapToPayPlugin.swift sits outside the iOS app target, contains no SDK integration — its nine Windcave references are all comments — and returns STUB_TOKEN_<timestamp>. It does not reach hardware. R7 owns the reality gate.
3. One crypto utility, not two. R5's key-ID envelope serves both legacy bank fields and Xero OAuth tokens. A simpler key-less format cannot rotate.
4. Three identity/authorisation flows share primitives, not blindly identical parameters. Google, Apple and Xero reuse canonical origin, one-time state, expiry, replay prevention, redaction and secure credential storage. OIDC nonce is required where an ID token is used; PKCE is required where the selected provider/client flow supports it. Apple account linking and Xero tenant consent remain protocol-specific. The existing Google route is the wrong implementation to copy — see R1-T4/T5.

Ground rules
Four conventions where the obvious approach is wrong here
1. New business database access goes through server/storage.ts and its two implementations. On the review snapshot IStorage declares 189 methods and extends the 8-method PaymentAttemptRepository; MemStorage is the in-memory/default-development implementation and DatabaseStorage is Drizzle/PostgreSQL. Three known routes.ts exceptions query uploadedFiles directly at lines 321, 3704 and 7076. Do not copy them: move them behind tenant-scoped storage during R1-T7. Every new operation still needs the interface signature, a MemStorage implementation and the real DatabaseStorage implementation. For MemStorage follow the existing precedent — database-required writes throw, list reads return [], and single reads return undefined. Never make MemStorage half-work.
2. server/routes.ts currently exports one registerRoutes(app: Express) with at least 220 registrations on the review snapshot: 215 GET/POST/PUT/PATCH/DELETE registrations plus five app.all registrations. Do not perform a broad router refactor during containment. New feature business logic belongs in typed service modules and thin registrations may remain in registerRoutes until a separate ADR approves modular routers. The route-policy generator must already understand app.all, app.use and mounted routers so a later refactor cannot escape the security inventory.
3. Schema imports are one exact line. Add to it; do not create a second import statement.
import { pgTable, text, serial, decimal, timestamp, boolean, integer, jsonb, uuid, uniqueIndex, index } from "drizzle-orm/pg-core";
4. Nothing applies schema on startup. Every change is a reviewed numbered SQL migration run by the separately approved migrate-first release step. Production startup is a read-only fail-closed migration gate; RUN_MIGRATIONS is retired and RUN_SCHEMA_PUSH is never a deployment mechanism. Never edit an applied migration, never use drizzle-kit push --force, and never deploy code that selects a new Drizzle column before the compatible migration is confirmed applied. Commit 8c22dc9 and migration 0017 completed the checked-in history; R0-T6A re-proves that on the owner-approved SHA, resolves any real fingerprint drift through forward work, and installs the continuous gate before Xero schema work.
Repository hygiene
   * Never git add -A or git add . — explicit paths only, always excluding .claude-home/** and .claude/settings.local.json.
   * Never edit an already-applied migration. Add a forward migration.
   * Never delete historical financial rows to make a test pass.
   * Never refresh a screenshot baseline, allowlist or expected error to turn a verifier green. Visual baseline changes need product approval.
   * Never put secret values, bank data, raw payment tokens, processor session IDs, return state, notification bodies or customer PII into evidence or commit messages.
   * Preserve unrelated dirty work; do not sweep it into a remediation commit.
What "done" means
A task is complete only when all of these hold. A TODO, stub, simulator or documentation promise is not an implementation.
   * The implementation exists.
   * A failing test was demonstrated, or the pre-change defect was otherwise captured.
   * Positive, negative, retry and no-side-effect tests pass as applicable.
   * Any schema- or data-changing migration was rehearsed on an isolated restored snapshot.
   * Logs and API responses expose no sensitive values.
   * Phone, tablet and desktop regression checks pass when client code changed.
   * The phase evidence record names the commit, commands, results, remaining risks, rollback point and human approvals.
Evidence lives at docs/evidence/remediation-v2-2/<phase>/. Commit sanitised text reports and small approved screenshots only — never database dumps, provider payloads, user invoices, trace archives containing tokens, or raw production exports.
Governance
   * Feature freeze. No new vertical, payment method, native capability, redesign or growth feature. Only incident containment, correctness and security fixes, required compatibility work, tests, operations and truthful documentation. Scope expansion needs a recorded product/security decision.
   * Decision log. docs/decisions/ holds one immutable dated ADR per decision, schema choice, retention choice or exception. Never rewrite an accepted ADR — supersede it.
   * Review before implementation. A reviewer completes the P8.5 template against the proposed phase; a second reviewer confirms every blocking finding is resolved. No implementation begins until the recommendation is Approve. "Approve with unresolved blockers" is not approval.
Engineering principles
   * Boring over clever — small typed services, explicit states, database constraints, observable retries.
   * Fail fast and fail closed — invalid target, config, state, identity, provider response or migration stops before side effects.
   * Never trust the client — authenticate, authorise, validate and derive tenant, money and provider identity on the server.
   * Money is traceable — every initiation, transition, refund, reconciliation and manual correction has an immutable local record and one accountable actor.
   * Reversible changes — expansion/compatibility/migration/contract releases, bounded locks, tested rollback. "Reversible" never means restoring a known vulnerability or reverting encrypted rows to plaintext writes.

const token = generateToken(authUser);

Required:

Validate issuer, audience, authorised party, nonce, time claims and exact redirect URI as applicable; do not force unsupported parameters into a provider flow.

X-T7AgentDurability-critical
Transactional outbox worker and ambiguous-response recovery
Depends on: X-T3, X-T6, R6 durable-worker primitives
Claim due rows atomically with FOR UPDATE SKIP LOCKED or equivalent finite leases. Enforce dependency order (contact → invoice → payment → credit note → allocation/refund payment). The local operation_key is stable for the operation's lifetime. Before the first mutating call, atomically persist one provider-key epoch and its exact request fingerprint. Retries inside that documented live epoch use the same Idempotency-Key and byte-equivalent method/endpoint/body; no worker invents a fresh key while the epoch is live. Mark complete only after storing the appropriate connection-scoped typed link/result in the same DB transaction. Bounded exponential backoff with jitter handles retryable failures; validation/permission 4xx becomes needs_attention; lease expiry permits safe takeover.
Xero currently caches idempotency keys for six minutes and says never to repeat one after expiry. Timeout/connection loss after a POST is therefore ambiguous. Before any mutating retry, query by stored Xero ID if known, otherwise by the deterministic document/contact/reference number and verify tenant, type, amount, currency, snapshot hash and status. Exactly one match is adopted. Multiple or mismatched candidates dead-letter and alert without another write. A zero match while the epoch is still live may retry the byte-equivalent request with that epoch's key. A zero match after expiry may, in one transaction, mark the old epoch reconciled_zero and create a new unique provider key linked to the same local operation; only then may the exact request be sent again. “Proved zero” requires the authoritative documented lookup plus any provider-documented indexing/visibility delay and repeated-read rule approved in X-H1—not one transient empty list. Never reuse the expired provider key and never rotate it without that proved-zero reconciliation record.
Check
Fault injection at claim, before send, after accepted response, before link commit, after link commit and during lease expiry produces one remote entity and one local link. Two instances cannot double-write. Virtual-clock tests straddle the six-minute boundary and prove same-key retry only inside the live epoch, no expired-key reuse, deterministic reconciliation before a replacement epoch, one atomic epoch lineage and no POST on multiple/mismatched candidates. Restart after the provider cache window reconciles instead of blindly POSTing. Dependency, poison-row isolation and dead-letter repair tests pass.

The non-negotiable rule
No Xero HTTP call occurs in a merchant payment, invoice-send, receipt or refund request. The local authoritative transition and its Xero outbox intent commit atomically; if that DB transaction fails, normal payment/refund reconciliation retries local finalisation from provider truth. After commit, Xero is asynchronous and cannot change the real TaptPay outcome. Failure stays durable in xero_outbox with append-only xero_sync_attempts, visible to the owner and operator. It is never converted into a local payment failure and never silently dropped.

Xero compliance checklist

   * Web app, not Custom Connection (single-tenant, wrong for multi-merchant SaaS).

   * Connection-generation-scoped typed link tables with real local FKs, transactional outbox and append-only redacted attempts; no direct Xero IDs on reusable domain rows and no unchecked polymorphic mapping.

P8.3
Stop conditions
Stop the phase, leave money initiation disabled, preserve evidence, escalate
   * The working/source branch changes after the approved R0-T0 SHA without rebaselining evidence.
   * A secret appears in a diff, log, artifact, screenshot or response.
   * Old rotated credentials still work unexpectedly.
   * Target database identity is uncertain.
   * Migration status shows pending, drifted, orphaned or unexpected applied entries.
   * Startup/build performs DDL, code selects a not-yet-applied column, or empty/restored migration fingerprints diverge.
   * Generated route inventory does not match runtime registrations, including app.all/app.use/mounted routers.
   * Backup, restore or decrypt proof fails.
   * A migration exceeds its rehearsed lock or statement budget.
   * Merchant A can read, mutate, export, upload for, refund or delete merchant B data.
   * Production-mode code can reach simulation, UAT, a stub token or an unapproved provider host.
   * Amount, currency, reference, session, share or provider environment mismatch can finalise.
   * Duplicate, concurrent or lost-response testing can double-charge, double-refund, double-count or double-notify.
   * An account/session bearer, refresh or OAuth credential reaches a URL, localStorage, log, analytics payload or non-Keychain native storage.
   * An ambiguous refund releases its reservation.
   * Subscription policy would block an intended active merchant.
   * Scheduler lease permits two money-job executors, or required jobs are stale without alert.
   * Plaintext backfill count rises unexpectedly, an envelope cannot decrypt, or an old-key backup cannot restore.
   * A hook crash, page error, console error, false-empty business state, device regression or broken tutorial appears.
   * A Release archive contains server.url, broad/unapproved navigation, UAT/live-reload hosts, an unsupported entitlement, fake wallet claim or forbidden external subscription CTA.
   * Apple monetisation, reviewer-payment path, privacy label or retention policy lacks the named approval.
   * A Xero operation has multiple/mismatched remote candidates, reuses a prior connection generation, exceeds a shared budget, or cannot prove whether an ambiguous POST succeeded.
   * Xero GST/payment/refund/settlement output differs from the immutable local snapshot or approved accounting examples by any cent, or a remote ledger correction has no compensating-action owner.
   * Real funds-model, PCI, native, privacy or legal claims lack named professional approval.
Do not mark a phase complete because time or context is running out. Record it incomplete with the exact blocker. Do not relabel an unexplained failure "flaky".

**The blank landing phone is fixed.** Shipped 2026-08-08 as `28e8b96`, on top of
the engine/scenes (`e78cc78`, `04f1180`).

The cause was never the 3D body: both iframes pointed at
`client/public/app/embed.html`, whose 10 hashed assets are gone, so the browser
refused the SPA-HTML fallback and React never mounted. Re-hashing was never a
fix — that snapshot is not regenerated by the Vite build.

Both iframes are now `<LandingPhoneMount className="tp-app-frame" bare>`.
`bare` renders the screen only (no rim/back/glare/island) so the demo sits
inside the landing's existing phone chrome rather than nesting a phone in a
phone. `initPhones()` still scales `.tp-app-frame` by `clientWidth / 390`, so
responsive sizing came free.

Two things that are easy to get wrong again if this is ever re-plumbed:

- **Measure `#tp-story-wrap`, not the phone.** The phone is pinned inside a
  `position: sticky` viewport, so its own rect yields a step function, not a
  story. `useStoryProgress(ref, active, trackSelector)` resolves the tall
  ancestor and reproduces the runtime's `(scrollY - storyTop) / storyLen`.
- **Do not gate the progress reading on visibility.** An IntersectionObserver
  only fires on threshold crossings, so a jump from above the story to below it
  goes 0 → 0 and fires *nothing*; progress froze and the phone sat on scene 1
  while the page sat past scene 8. Reproduced at 1440×900, where the story is
  already outside the viewport at scroll 0. §6 rule 9 still holds: outside the
  story the value pins to 0 or 1, so `setProgress` no-ops.

Industries tabs pick the scene via `[data-ind]` → `INDUSTRY_SCENE` in
`manifest.ts`. **Never import `scenes/registry` from `landing-page.tsx`** — that
pulls all eight scenes into the main chunk and breaks §6.

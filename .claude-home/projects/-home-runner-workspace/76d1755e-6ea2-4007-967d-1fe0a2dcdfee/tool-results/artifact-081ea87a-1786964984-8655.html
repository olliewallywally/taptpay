Diagnosis & plan · phone merchant app

The 44-pixel rule

Five separate mobile bugs were reported. Four of them are the same bug: one blanket CSS rule that silently inflates every button in the app below 640 px — and only below 640 px, which is why nothing in the test suite has ever seen it.

2026-08-17 branch feat/tablet-desktop-app measured in-browser · 7 phone sizes status diagnosis complete, no code changed
01

What's actually wrong

Finding

One rule, four symptoms

client/src/index.css:360 applies min-height: 44px; min-width: 44px to every <button> in the app inside a @media (max-width: 640px) block. min-height beats height, so no component can set a smaller box. The action bar's buttons ask for 27 px and render at 44. The highlight bubble is a <div>, so it stays 27.

Because the query is max-width, tablet and desktop never see it — and every probe in scripts/desktop-shots/ runs at 1194 px or wider. The bug is invisible to the entire existing suite by construction.

A sixth cause explains the intermittency — why it "keeps breaking" rather than simply being broken. And a seventh explains why none of it was caught.

Seven root causes

Causes
RC-1

So the action bar is a 56 px lozenge inside a 37 px row, holding a 27 px highlight bubble behind a label centred in a 44 px box. A/B proof: disabling only those two declarations at runtime takes the stack header from 44 px → 24 px with nothing else changed.

The same media block (lines 360–473) is a legacy dark-glass override set that still fires on every modern mobile page: label { color: white !important }, input { background/border/color !important }, table … { background: transparent !important }. Not the reported bugs, but the same failure mode, and it will keep producing "padding is wrong" reports.

RC-2

The bubble is half-measured, half-hardcoded, and never re-measured

RetailTerminalViewCore.jsx:89–109

measure() returns { x, w } only — top: 5px and height: 27px live in CSS. The bubble is guaranteed wrong the moment a button's real height differs from 27, which RC-1 makes permanent. The effect also depends on [activeIdx] alone, with no ResizeObserver: resizing 390 → 320 leaves the bubble 14.5 px off its button, permanently. On a real phone that fires on rotation, on the keyboard opening, and on the iOS URL bar collapsing.

RC-3

Layout is absolute-pixel choreography around floating chrome

RetailTerminalViewCore.jsx:318–374 · 28 such panels across three verticals

<div style={{ height: '50%', padding: '100px 28px 28px' }}>   {/* hero  */}
<div style={{ flex: 1,      padding: '154px 22px 90px'  }}>   {/* stack */}

154px is a guess at the floating FAB + action bar's footprint; 90px a guess at the dock's. Nothing measures either — and the dock collapses 78 px → 44 px after four seconds of idle while the padding never reacts.

Plus 194 hardcoded px values in the retail CSS. The amount is fontSize: 88 at ten call sites. $99999.99 measures 430 px — it clips on the largest phone made. On a 320 px phone the wrap pushes the hero to y: -162 and the split-bill pill to y: -78: both entirely above the top of the screen.

RC-5

Wrong viewport unit, no safe areas

The retail terminal uses height: 100vh; every other mobile surface in the app uses 100svh. On iOS Safari 100vh is the large viewport, so with the URL bar showing the terminal runs 60–100 px past the visible area — the bottom of the stack and the dock fall below the fold, on top of RC-3's squeeze. viewport-fit=cover is set, but the terminal uses no env(safe-area-inset-*) at all: the notch is cleared with a hardcoded padding-top: 100px and the home indicator not at all.

RC-6

Three unscoped copies of the same global stylesheet

the intermittency

Retail's TP_CSS and property's TP_TERM_CSS are both injected as unscoped global .tp-* rules with identical selectors and different values — property adds transform: scale(0.85) and z-index: 2 on the bubble, which paints it over the label instead of behind it. Trades is correctly scoped. Measured on /property/terminal: two <style> tags defining .tp-subbar live at once, and the bar renders 241×48 instead of 316×56. Whichever tag is later in the DOM wins.

RC-7

The only mobile gate proves nothing about layout

scripts/verify-mobile-retail-regression.mjs

One viewport (390×844). It asserts the outer box is 390×844 with no horizontal scroll, plus API-contract checks. It passes today, against every screenshot behind this document. It never measures an internal component, never changes size, never rotates, and never simulates a safe area. Fixing the five symptoms without fixing this is how they come back.

04

The plan, in order

Execution

Two stop conditions: Phase 3 can't start before Phase 1 lands (the invariants can't hold while RC-1 is live), and Phase 4 can't start before Phase 2 (the grid needs the tokens). Phases 5 and 6 are independent of each other.

0

Land the gate first — failing

Write scripts/verify-mobile-responsive.mjs before touching any UI, and record today's numbers as the baseline. A fix with no gate is a fix with a half-life.

Gate: probe runs and reports the current failures

1

Remove RC-1 without losing touch accessibility

The 44 px rule exists for a real reason. Give the hit area back without touching the layout box — a pseudo-element is part of its element for hit-testing, so the tap region grows while the painted box and every sibling's position stay as designed. Then audit the rest of the 640 px block as one unit; keep the font-size: 16px on inputs that prevents the iOS focus zoom. 

.tap-target { position: relative; }
.tap-target::after {
  content: ""; position: absolute; left: 50%; top: 50%;
  transform: translate(-50%, -50%);
  width: max(100%, 44px); height: max(100%, 44px);
}

Gate: the new probe + a full visual sweep — this changes every mobile page

2

The responsive foundation

One token layer on .tp-viewport: a design ratio --u: clamp(0.84, calc(100cqi / 390), 1.10) driving spacing and type, the svh/dvh fallback chain, and real safe-area insets. Container units rather than viewport units, so the same components stay correct inside the landing page's phone demo and on a tablet.

Gate: no horizontal scroll, no edge-crossing box, no clipped text — six sizes

3

The action bar, unable to diverge

One shared SegmentedBar for all three verticals. Put the buttons and the indicator in the same CSS grid row so the bubble's height is the button's height — whatever RC-1-shaped rule appears next. Keep measurement only for the sliding transform, and add a ResizeObserver plus a document.fonts.ready re-measure. The split-bill pill takes var(--bar-h), so "exactly the height of the action bar" becomes a token, not two numbers that happen to match.

Gate: bar height fixed; bubble ≡ active button; label fully inside bubble; send ≡ bar; never clipped; all still true after a resize

4

Terminal home: measured gutters, three-row floor

Replace height: 50% + magic padding with a three-row grid whose middle row is the measured height of whatever chrome is actually floating, and whose stack row has min-height: calc(3 × var(--row-h) + var(--stack-hdr-h)). "At least three" stops being an outcome and becomes a CSS invariant. Pin the header outside the scroll container. On short screens the hero contracts first — the stack floor is non-negotiable.

Gate: visibleStackRows >= 3 on all six sizes

5

The money display fits its box

white-space: nowrap plus font-size: min(var(--amount-max), calc(100cqi / var(--amount-chars) × k)), with React setting the character count. Deterministic, no measurement, no reflow loop, trivially assertable. A useFitText fallback covers late font loads, with a floor below which the presentation compacts rather than shrinking into illegibility. Applies to all ten call sites, not just the hero.

Gate: the amount's box sits inside its parent at the maximum value, six sizes

6

Scope the stylesheets, extract the primitives

Scope retail and property under their own class the way trades already is; better, move all three out of template literals into real .css files so Vite dedupes them and they stop being re-parsed on every mount. Then extract the shared primitives — bar, amount, stack row, pill, field, CTA — so the next fix lands once instead of three times.

Gate: no unscoped .tp- selector survives the grep

7

Make the gate permanent

Six viewports × every mobile route × both orientations, with the component contracts as hard assertions, a re-measure after a size change, and runs with a simulated safe area and a collapsed dock. Plus four cheap CI greps that catch the cause: no min-height on a bare element selector inside a media query; no new fontSize literals or height: '50%' under features/terminal/; no 100vh on a phone surface; no unscoped .tp- rule in a style literal.

Gate: wired in beside verify-desktop-p0.mjs, exiting non-zero

05

Four calls that are yours

Decisions

These change the shape of the work. The plan above assumes the recommended answer, and a different answer only changes Phases 2, 4 and 5.

D1 · Adaptation strategy

Fluid / intrinsic layoutrecommended — tokens, clamp(), container queries, measured gutters. Everything reflows and type stays a readable physical size on every device.

The alternative is the scaled canvas the desktop app already uses: design once at 390×844 and transform: scale() to fit. Cheap and pixel-perfect — but text goes physically tiny on a 320 px phone and tap targets scale below the minimum. Right for simulating a laptop on a tablet; wrong for a real phone.

D2 · Smallest supported phone

The plan assumes 320×568 — iPhone SE 1st gen, older Android, and any iPhone in Display Zoom. That's the size where three stack rows plus a hero genuinely don't fit without the hero contracting, and it may need a compact row variant. If 360×640 is the real floor, every clamp minimum relaxes.

D3 · Blast radius of the RC-1 fix

Removing the blanket rule changes the rendered height of 5–13 buttons on every mobile page — mostly back toward the original design. One sweeping commit plus the gaterecommended, because a half-applied fix leaves two inconsistent button systems live at the same time.

D4 · Money formatting

fmt() produces $99999.99 with no thousands separator. Should it be $99,999.99? Grouping widens the string, so the fitter has to be calibrated for whichever you want. Current maximum is 7 digits.

Measured against the dev server on :5000 with the nix Chromium, using scripts/desktop-shots/retail-fixtures.mjs for auth and API mocks, at hasTouch: true, isMobile: true. Seven phone viewports, three screens each, plus a resize pass and a cross-vertical navigation pass.

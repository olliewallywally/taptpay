Tablet and desktop are the same code

App.tsx:906-909 routes both device classes to DesktopPropertyTerminal. The only difference is that DesktopFrame letterboxes desktop into a 13″ slate and lets tablet bleed full width. Everything below lands on both, so every new control is sized for touch as well as pointer.

Rules the pass must not break

The 2c design language is narrow. Every addition below reuses something already on the page rather than inventing a new visual idea.

Geometry

Canvas is 1180×880: a 66px header, a 1px divider, then .tapt-desktop-main at 1180×813. A design y maps to y − 66. The right panel's usable height is 787px and its usable width is 466px; existing blocks size to 430–445px, so stay in that band.

No position: fixed, ever

The canvas sits inside transform: scale(…), so fixed positioning becomes scale-relative — the exact trap already recorded against ReportModal. Every overlay here is position: absolute inside a relative ancestor on the page. And no window.confirm: it paints browser chrome over the simulated 13″ frame, so destructive confirmation is two-step and in-surface.

Cascade

.dt-cascade > * and .dt-rise ship opacity: 0 under an animation: … both fill, so a block carrying either class that never animates is permanently invisible, not merely un-animated. New top-level blocks in .pt-left shift the --dt-i step numbering — the rail is 6, the panel is 7. Never transform a rail slot: it becomes the containing block for the absolutely-positioned rail and moves it.

Palette and prefix

Class prefix stays pt-, in the one page-scoped CSS template literal. New states reuse the file's ten colour constants: pressed is ACTIVE on NAVY text, unpressed is ACCENT_SOFT on transparent with a rgba(94,158,255,0.5) border, destructive is RED, confirmed is GREEN. New primary actions are ≥ 40px on their short axis for touch; new chips match the sizes already on the page.

The phases

1

Money correctness

bugno visual change

The heroes and row amounts use amountCents, so a 4-way split with three shares paid reports its full value as outstanding. The phone uses the server-computed owingCents. The live set is a blacklist rather than the phone's whitelist, and row names resolve from the archived-filtered tenant list — so an archived tenant's live invoice renders as "tenant".

  • Extract the model to desktop/data/property-terminal-model.ts, matching the desktop/data/* convention, with a unit test beside it.
  • owing(i) = i.owingCents ?? i.amountCents ?? 0 for both heroes and row amounts, so the column and the figures agree.
  • Live set becomes the phone's whitelist: pending_dispatch, dispatched, overdue, dispatch_failed.
  • Names come from the server's enriched inv.tenantName, with the tenant map as fallback.
  • Keep bucketing pending_dispatch under sent — the phone's filter hides those rows, which is worse — but add a separate label so the row reads awaiting send instead of claiming it was sent.
2

Send-flow safety

bugno new UI
  • Keypad zero-guard. Confirming an empty keypad silently sets the amount to $0. Dim the confirm circle to opacity 0.45 and return early — mirroring .pt-send-btn:disabled, the file's existing disabled language.
  • Post-send reset. Tenant and amount both survive a successful send, so a second click issues a second invoice. Zero the amount on success; keep the tenant, which is the useful desktop state. The 1.6s flash covers the transition.
  • Description clobber. Picking a charge chip unconditionally overwrites typed text. Port the phone's rule: only overwrite when the field is empty or still holds a preset.

This phase creates client/src/desktop/property-terminal.test.tsx, modelled on retail-terminal.test.tsx. There is currently no test at all for this page — none of the nine defects behind this plan would have been caught by CI.

3

Row actions

new surface

The phone has an action sheet on every request row. Desktop rows are inert <div>s, and /invoices/:id/resend and /invoices/:id/void have no caller anywhere in the desktop app.

  • An anchored popover in the left column — not a mode, not a modal. It reuses the panel already shipped as .ph-scope-menu on property home: #0B1436, radius 14, blue hairline, soft shadow.
  • .pt-rows scrolls, so a popover inside it clips. Render it as a child of .pt-stack, offset by row.offsetTop − scrollTop. Use offsetTop, not getBoundingClientRect() — offset values are pre-scale and need no division by the canvas scale.
  • Contents branch the way the phone's do: settled invoices get a message, charges get resend link, rent gets edit amount & resend, then mark received and cancel invoice.
  • Cancel is two-step in-surface: the popover swaps to a red "this can't be undone" with confirm / back.
  • Both new mutations call notifyIfBillingCardRequired on failure. The phone omits it here, but the desktop send paths already do it and a silent 402 on a resend is the kind of thing this branch has been bitten by.
4

Deep links and remind

behaviourneeds phase 3

The desktop property home already links to ?mode=reminder and ?mode=expense, and the terminal reads no query parameters at all — so both quick actions silently open the default request panel.

  • Read them in a useState initializer, following property-clients.tsx and trades-terminal.tsx. Don't port the phone's 800ms replaceState strip — that hack exists because its route transition can discard the first mount.
  • mode=expense opens bill; mode=reminder filters to overdue and reveals the remind buttons; stack= sets the filter; client= preselects a tenant, matching 2b's param name.
  • Remind button on overdue rows, on the phone's exact rule, calling Phase 3's resend mutation. ~28px tall so it sits inside the 40px row.
5

Bill completeness

controls

Every desktop bill is hard-coded due on receipt, with no way to say otherwise, and can't carry the supporting document the phone uploads. The attach omission was logged as deliberate — "worth its own pass rather than a cramped port". This is that pass.

  • Due chips in the existing label-then-chips rhythm: on receipt / in 7 days / in 14 days, defaulting to 7, in a grid mirroring .pt-freq-chips so the two screens' chip rows are the same object.
  • Attach invoice — a label-wrapped hidden file input styled as a 50px dashed row at radius 12, matching .pt-field-row rather than the phone's 16. Uploads on pick with the phone's 20MB guard; attached state swaps to filename plus remove.

Vertical budget. Bill mode currently uses ≈468px of the 787px panel. Due adds ≈96, attach ≈102 → ≈666, leaving 121. Phase 6's split row takes ≈62 of that → ≈728, 59px spare. Reclaim 40px while you're in there by tightening .pt-bill's top margin and the four label margins. Screenshot both device classes and confirm nothing crosses 813px — 3c's compose block failed exactly here.

6

Split

controlsquestion 1

Desktop hard-codes splitEnabled: false on both mutations and renders no split state at all. The phone offers split on a rent request and on a bill, and shows paid/count split plus "left of $X" on part-paid rows.

  • One more .pt-field-row on both the request and bill panels: split glyph, "split this bill", toggle. It reuses the 54px row already used twice above it, so the lower block reads as three consistent rows plus chips.
  • .pt-switch is the one genuinely new component in this plan — worth defining rather than substituting a chip, because Phase 7 reuses it.
  • In the request list: a green paid/count split badge, and a "left of $X" caption stacked under the amount the way .pt-tc-right already stacks amount over caption.
7

Automation mode

new mode

Desktop can create recurring rent and then gives the merchant no way to see, pause or cancel it. The desktop trades terminal already ships this surface, so it's a desktop-internal inconsistency as much as a phone gap.

  • A sixth rail button, and tighten the rail's gap from 40px to 32px at the same time: six buttons at gap 40 makes the rail 547px tall ending at y=748 and visibly bottom-heavy; at 32 it's 507px ending at y=708, growing by one button height rather than a button plus a gap.
  • usePropertySchedules() already exists in property-data.ts — use it, don't add a query. One new query for reminder settings, optimistic like the phone's.
  • Overdue reminders block: title, sub, the Phase 6 toggle, then remind after / repeat every / max reminders chip rows and the summary sentence. Render it in the page's blue language, not the phone's amber card — amber on this page means overdue, and an amber panel here would read as an alert.
  • Active schedules list reusing .pt-paid-row's geometry, with a state pill, next-run date, pause/resume and a two-step cancel.
8

External reference

control

markPaid hard-codes the reference to null while the column exists and the phone captures it. Keep the flat list — clicking a row's check expands that row in place with a slim input and confirm / cancel, other rows untouched, one row open at a time.

9

Scope chip

cleanupquestion 3

The "all properties" chip has no onClick and no state — a dead control, while property home has the identical chip fully wired. Recommendation: wire it. Port the home's scope pattern, derive the address list from active tenants only so the known "archived-only properties remain selectable" defect isn't reintroduced, and let both heroes, the request list and the mark-paid list follow the scope. The tenant picker does not — you may need to bill a tenant outside the current scope.

Questions for Oliver

Answer before Phase 5. Phases 1–4 can start now.

01
Split was deliberately deferred. Un-defer it?

The bill's split toggle was logged as a deliberate omission. This plan un-defers it and also adds split to the rent request, which the phone has and desktop never did.

02
Should the bill keep its pre-selected charge type?

Desktop pre-selects "water / utilities", so a bill can go out without the type ever being chosen; the phone forces an explicit pick.

Recommend keeping it — all five chips are visible at once and the design shows a selected chip — but this is the one I'd happily reverse.

03
Scope chip: wire it or delete it?

Recommend wiring. A dead control is worse than either outcome.

04
The phone's unreachable screen: wire it up or delete it?

See below — it's a phone commit either way, not tablet work.

Out of scope: the phone's dead screen

BatchAndAutoScreen implements batch send, schedule management and reminder settings on the phone in ~140 lines, and nothing navigates to it. The subbar covers only tenants / send / bill / external, and there is no go('batch') anywhere in client/src — the only surviving reference is a busy.batch key in a test fixture. batchMutation is dead with it.

So schedule management and reminder settings are missing from both clients, and Phase 7 is new functionality rather than parity. Wire it up — a fifth subbar slot, which also gives the phone batch send — or delete it, since once Phase 7 lands an unreachable duplicate of the same UI is a liability. Either way it's a phone commit and doesn't belong in this branch's screen-at-a-time queue.

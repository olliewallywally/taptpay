# Plan — lightweight, pixel-faithful landing-page phone demo

Date: 2026-08-07
Branch: `feat/tablet-desktop-app`
Status: **planned, not started**

This plan replaces the broken app surface inside the landing page's 3D phone and
makes every phone-focused story beat visibly perform the workflow described by its
copy. The result must look indistinguishable from the current 390 × 844 mobile app
for the states it shows, while remaining a tiny, deterministic marketing demo with
no authentication, API, payment-provider, messaging, or other live side effects.

The performance requirement is a release gate, not an optimisation to attempt at
the end: the complete phone feature has a hard compressed-transfer budget of
90 KB, and visitors who do not approach the phone story must download zero
phone-specific bytes.

---

## 1. Confirmed current failure

The 3D phone body is not the blank-screen failure. Browser verification at
1440 × 900 and 390 × 844 confirmed that `#tp3`, `#tp3-gl`, the CSS face, and a
WebGL context are present and visible.

The screen iframe is empty because `client/public/app/embed.html` references a
deleted set of hashed JavaScript and CSS assets. The missing asset requests fall
through to the SPA HTML response, which the browser rejects for strict MIME-type
mismatches. React never mounts inside the iframe.

Simply changing those hashes is not a durable fix:

1. The embedded snapshot is not regenerated by the normal Vite build.
2. The old mock-auth/API bootstrap and hash-router path no longer exist.
3. Current merchant routes are protected and bind to React Query, SSE, and live
   mutations.
4. Loading the real app in an iframe would duplicate the application runtime and
   turn a marketing animation into a large, fragile, side-effectful surface.
5. Most current story beats only swap hashes. Utility bill and split bill scan all
   iframe buttons with `/bill/i` or `/split/i`, click the first match after a fixed
   timeout, swallow every error, and never verify completion.

Current measured payloads provide the baseline:

| Item | Current size |
|---|---:|
| `landingRuntime` chunk | 670,999 B raw / 175,271 B gzip |
| Current embedded app's eager JS/CSS references | 987,129 B raw before route chunks |
| Existing phone front/back WebP textures | 36,702 B total |
| Landing's eight local OTF font files | 127,088 B total |

## 2. Non-negotiable product requirements

1. The phone must remain a convincing rotating 3D object on desktop, tablet, and
   physical-phone landing viewports.
2. Every displayed app state must be visually indistinguishable from the current
   mobile app at its canonical 390 × 844 layout: typography, colours, spacing,
   controls, icon treatment, navigation, transitions, and confirmation states.
3. “Replica” means the visible states and scripted actions shown in the landing
   story, not a hidden copy of the entire production application.
4. Every action is deterministic and local. The demo must never create an invoice,
   schedule, quote, transaction, split, card session, upload, notification, email,
   SMS, share, download, permission prompt, or external navigation.
5. No full production page may be mounted merely to reuse its appearance. Only
   small, side-effect-free helpers or extracted presentational primitives may be
   shared.
6. The existing mobile merchant app is unchanged. The landing demo must not alter
   phone routing, authentication, API contracts, or production component state.
7. There are no videos or per-scene screenshots. The replica is live HTML/CSS so
   it stays sharp, animates properly, and compresses well.
8. The demo must remain useful without WebGL, on reduced-motion devices, and when
   the browser's Save-Data preference is enabled.

## 3. Architecture decision — CSS 3D, not Three.js

Remove Three.js from the landing page entirely.

The phone body will use CSS 3D transforms with:

- the existing 9 KB front and 28 KB back WebP shell textures;
- front and back faces with `backface-visibility`;
- a gradient rim and side-button layers;
- perspective, `rotateX`, and `rotateY` driven by CSS custom properties;
- the existing glare, glow, and shadow language;
- a real DOM app screen on the front face.

This preserves the perceived 3D rotation while removing the current WebGL library,
renderer, geometry, materials, lighting, texture-loader, and perpetual render loop.
The hero coins must also move off Three.js; use a handful of CSS gradient coins or
one tiny reusable inline SVG treatment. They remain decorative and must not justify
retaining a 175 KB-gzip runtime.

The app screen is a direct React child of the phone face, not an iframe. It reuses
the page's existing React runtime, cannot drift through hashed build snapshots, and
needs no cross-window readiness protocol.

### 3.1 Lightweight demo state

Define a typed scene registry and one small reducer:

```ts
type LandingPhoneScene =
  | "overview"
  | "rent-weekly"
  | "property-bill"
  | "trades-invoice"
  | "quote-deposit"
  | "retail-sale"
  | "retail-split"
  | "checkout-wallet";

type LandingPhoneState = {
  scene: LandingPhoneScene;
  step: number;
};
```

Only the current scene is rendered. Scenes share compact primitives—phone chrome,
top bar, amount keypad, person row, field row, segmented control, status row,
primary action, success card, progress bars, and checkout wordmark—rather than
shipping seven independent page trees.

Fixtures are fixed, typed, and deliberately small. Use a fixed demo date so text
and screenshots never vary by timezone or test day.

### 3.2 Scroll control

The existing story is eight equal zones: intro plus cards 01–07. Preserve that
narrative, but replace hash changes and delayed DOM clicks with explicit scene and
step selection.

Within each zone, map local scroll progress to discrete milestones. CSS transitions
animate between milestones. The controller emits only when the scene or step
changes; it does not set React state on every animation frame.

Required behaviour:

- entering a zone resets it to its defined starting state;
- scrolling forward advances through every milestone;
- scrolling backward rewinds deterministically;
- jumping or fast-scrolling lands on the correct final milestone;
- no timeout from an old scene can fire after the scene changes;
- offscreen scenes perform no work;
- reduced-motion/Save-Data users receive a clear completed state rather than a long
  animation.

### 3.3 Secondary Industries phone

The flat/tilting phone in Industries uses the same renderer and scenes:

| Tab | Default scene |
|---|---|
| Property | `rent-weekly` |
| Trades | `quote-deposit` |
| Retail | `retail-sale` with split available |

“Try it live” enables local tap-through controls and a replay action. It never
enables production network behaviour. On narrow viewports the existing “see it
live” reveal remains, but the revealed phone must be fully readable and usable.

## 4. Exact story scenes

### 4.1 Overview

Show the current mobile home language and briefly introduce Property, Trades, and
Retail. This is an overview, not a transaction. Finish in the Property context so
the transition into weekly rent is coherent.

### 4.2 Property — weekly rent collection

Mirror the current Property terminal flow:

1. Open rent-request mode.
2. Select `Mia · 18 Tui St`.
3. Enter `$620`.
4. Select **weekly**.
5. Show `first request now, then weekly from …`.
6. Press **send & automate**.
7. Show the sent confirmation.
8. Finish on an active schedule card: `$620 · weekly · active`.

The landing scene never POSTs the invoice or schedule endpoints.

### 4.3 Property — utility bill

1. Enter bill/expense intent.
2. Select the tenant.
3. Enter `$86.40`.
4. Select/type `water` and the due option.
5. Display a pre-seeded `water-invoice.pdf` chip; do not open a file picker.
6. Send.
7. Show `bill sent`, then the tenant-history status moving `sent → paid`.

### 4.4 Trades — quick invoice

1. Open Quick Invoice.
2. Select the fixed client.
3. Enter `$480` on the keypad.
4. Add `emergency callout`.
5. Send.
6. Show `invoice sent`.
7. Return to the current jobs surface with the new row and a paid-status flourish.

### 4.5 Trades — quote to deposit

1. Choose the fixed client.
2. Add `Heat pump service`, quantity 1, `$1,250`.
3. Enable **require deposit**.
4. Select 20% and show a `$250` deposit.
5. Send the quote.
6. Crossfade to the current customer quote card.
7. Show **view quote**, then **confirm**.
8. Finish on the `$250` deposit checkout request.

Quote totals must use the same pure GST/deposit maths as production. Do not mount
the API-bound Quote or Checkout pages; the real quote GET itself has side effects.

### 4.6 Retail — normal sale

1. Open the keypad and enter `$12.50`.
2. Set `flat white ×2`.
3. Confirm the sale.
4. Show the current share/QR state without a working external link.
5. Move the item into the payment stack.
6. Transition `awaiting payment → paid`.

### 4.7 Retail/customer — split bill

1. Create a `$120` merchant transaction.
2. Enable **split bill** and confirm it.
3. Crossfade to the customer split page.
4. Increase the count to four people.
5. Show `$30 each`.
6. Confirm/pay one share.
7. Animate progress from `1 of 4 paid` to `4 of 4 paid`.
8. Finish on **All done!** and the receipt confirmation.

This must visibly demonstrate setup, customer choice, confirmation, and completion;
merely toggling the split control does not satisfy the requirement.

### 4.8 Customer — wallets and confirmation

1. Open the branded `$250` deposit checkout from the prior quote story.
2. Highlight Apple Pay, Google Pay, and credit/debit card affordances in sequence.
3. Select the deterministic demo method.
4. Show a short local processing state.
5. Finish on `Payment confirmed` and the branded receipt state.

No Windcave SDK, hosted fields, wallet API, session request, redirect, or provider
script may load.

## 5. Visual-fidelity contract

The current 390 × 844 mobile screens are the visual source of truth. Before
building each scene, capture its real source states with controlled fixtures. The
demo must match:

- the exact landing-visible copy and numeric formatting;
- Outfit/Larken typography, weights, line heights, and letter spacing;
- navy, sky, cream, status, and disabled colours;
- control dimensions, corner radii, borders, shadows, and spacing;
- navigation/chrome visible in the corresponding real screen;
- keypad, selector, toggle, progress, confirmation, and receipt behaviour;
- transition direction and duration, within reduced-motion rules.

Automated screenshot comparison is required for every scene's important starting,
action, and final states. Literal zero-pixel equality across operating systems is
not a valid promise because font rasterisation differs; the acceptance standard is
visually indistinguishable at normal viewing and no unexplained structural or
colour diff in the controlled Chromium baseline.

Do not import a large production component merely to win a screenshot. Extract a
small presentational primitive only when doing so keeps both production and demo
semantics clear and does not pull API/query/motion dependencies into the landing
graph.

## 6. Transfer and runtime budgets

Budgets are measured from a clean browser cache using compressed network transfer,
not only source-file size.

| Resource | Target | Hard failure |
|---|---:|---:|
| Phone-specific bytes before the story approaches | 0 KB | > 0 KB |
| Demo JavaScript | ≤ 30 KB gzip | > 35 KB gzip |
| Demo CSS | ≤ 6 KB gzip | > 8 KB gzip |
| Phone images | ≤ 37 KB | > 40 KB |
| Entire incremental phone feature | ≤ 70 KB | > 90 KB |
| Extra network transfer when changing scenes | 0 KB | > 0 KB |

Rules used to meet the budget:

1. Dynamically import the phone demo only when an IntersectionObserver reports the
   story is close enough to need it. Do not import it immediately on landing mount.
2. Do not prefetch it for Save-Data users. Show the compact static completed state
   until the story itself enters view.
3. One compact chunk contains all scene data and primitives; avoid seven requests
   and duplicated module wrappers.
4. No Three.js, Framer Motion, React Query, Radix, Lucide, charting, QR, PDF, or
   payment-provider imports in the phone chunk.
5. Use CSS transitions and tiny inline SVG paths. Do not ship icon packs.
6. Optimise the two shell textures and choose AVIF/WebP only when the measured
   result is smaller and visual alpha quality is unchanged.
7. Reuse fonts already required by the landing page. The phone adds no font file.
8. Separately subset/convert the landing's local font files to WOFF2 and load only
   required weights if side-by-side typography remains unchanged; record this as
   total-landing savings, not as a phone-budget trick.
9. Stop animation work while the story is outside the viewport or the document is
   hidden. Use transforms and opacity only.
10. Hash and cache immutable assets. A repeat visit should transfer no unchanged
    phone asset.

A small verification script must print the raw, gzip, and Brotli sizes of the phone
chunk/CSS/assets and exit non-zero on a hard-budget breach.

## 7. Resilience, accessibility, and lifecycle

1. The DOM screen mounts independently of enhanced 3D effects, so an effects error
   can never produce a blank phone.
2. Provide a deliberate static CSS shell fallback for unsupported 3D transforms.
3. Use `prefers-reduced-motion` and the existing explicit reduced-motion prop.
4. Story content needs meaningful accessible labels. Decorative shell layers and
   hero coins are hidden from assistive technology.
5. Only the interactive Industries copy enters the tab order. The scroll-driven
   cinematic screen is a labelled demonstration rather than dozens of phantom
   controls.
6. Confirmation changes use a restrained polite announcement; intermediate
   animation steps do not spam a live region.
7. Add a real runtime `destroy()` path. It must remove listeners, observers, and
   animation work when the landing route unmounts.
8. Delete the unreachable legacy cinema implementation and its duplicate beat list
   after parity is verified.

```text
  primitives.tsx

```

`landing-page.tsx` owns the lazy boundary and the two demo instances.
`landingRuntime.ts` retains the broader landing scroll/chrome behaviour but loses
Three.js, iframe routing, regex clicking, fixed action timers, and dead legacy
cinema. The scene registry is the one source of truth used by cinematic and
Industries phones.

## 9. Implementation phases

### P0 — freeze references and budgets

- Capture controlled current-app reference states for all seven workflows.
- Record the current landing request graph, raw/gzip/Brotli sizes, and main-thread
  behaviour.
- Add named `data-demo-scene` and `data-demo-step` acceptance selectors.
- Add failing skeleton tests for the budgets and scene registry.

### P1 — remove the broken delivery path

- Mount a minimal direct DOM screen in both phone locations.
- Remove iframe source/defer/live-pointer logic and the landing dependency on
  `app/embed.html`.
- Prove that no `/app/assets/*` or protected merchant route is requested.
- Add loading, error, and static fallback states.

### P2 — replace WebGL with CSS 3D

- Rebuild front/back/rim/button/glare layers with CSS perspective.
- Port the current scroll rotation to CSS variables.
- Replace hero WebGL coins with CSS/SVG decoration.
- Remove Three.js from the landing dependency graph and verify the compressed
  decrease before proceeding.

### P3 — shared demo engine

- Implement the typed registry, fixed fixtures, reducer, and shared primitives.
- Map every story zone's local progress to explicit steps.
- Implement reset, rewind, jump, offscreen pause, Save-Data, and reduced motion.
- Wire the same engine to Industries tab and replay controls.

### P4 — scene implementation in parallel

After P3 is stable, split work into independent lanes:

- Property: weekly rent and utility bill.
- Trades: quick invoice and quote/deposit.
- Retail/customer: normal sale, split bill, wallets/confirmation.

Each lane finishes its unit states and screenshot comparisons before integration.

### P5 — integration and polish

- Tune desktop/tablet phone position and cinematic text balance.
- Ensure the physical-mobile landing view keeps the phone and HUD readable with no
  horizontal overflow.
- Verify the Industries reveal and interaction at narrow widths.
- Consolidate styles/primitives after visual approval to remove duplicate bytes.

### P6 — final acceptance

- Run typecheck, complete Jest, production build, size gate, and browser matrix.
- Capture the complete story at desktop, tablet, and physical-mobile viewports.
- Test forward, backward, fast, and jump scrolling.
- Test Save-Data, reduced motion, unsupported 3D, and unmount/remount.
- Inspect the production request graph and compressed transfer from a clean cache.

## 10. Required verification

### Automated

- `npm run check`
- focused scene/reducer tests
- full `npx jest --runInBand`
- `npm run build`
- `node scripts/verify-landing-phone.mjs`
- `git diff --check`

The browser verifier must cover at least 1440 × 900, a representative landscape
tablet, and 390 × 844. It must assert:

- a visible phone body and non-empty screen;
- the expected scene and milestone at every story position;
- weekly rent reaches an active schedule;
- utility bill reaches sent/paid history;
- trades invoice reaches its sent/result state;
- quote reaches the deposit request;
- retail sale reaches paid stack state;
- split bill reaches setup, four-way confirmation, progress, and completion;
- checkout reaches payment confirmation;
- Industries tabs select the correct workflow and replay safely;
- reverse/fast scrolling cannot leak a stale scene;
- no first-party console/page/failed-request errors;
- no `/api`, `/app/assets`, auth, SSE, provider, analytics-from-demo, or external
  action request;
- no production merchant page/component chunk is loaded;
- no new resource is fetched when changing scenes;
- CSS fallback works with enhanced effects disabled;
- route unmount/remount does not duplicate listeners or animation work;
- every compressed size remains inside the hard budgets.

### Visual review

For each source state, compare the real app and demo at the same 390 × 844 logical
viewport. Review typography, geometry, colour, clipping, scrolling, dynamic island,
navigation, and final confirmation. Compile desktop/tablet/mobile contact sheets for
the complete landing story.

## 11. Definition of done

This work is complete only when:

1. The landing phone never shows a blank screen.
2. The seven advertised workflows visibly perform and finish their matching action.
3. The visible demo states are indistinguishable from the current mobile app in the
   controlled visual baseline.
4. The complete phone feature stays below 90 KB compressed and makes no per-scene
   downloads.
5. Visitors who remain above the story download no phone-specific payload.
6. Three.js and the frozen app iframe are absent from the landing request graph.
7. The demo makes no real or external side effect.
8. Desktop, tablet, physical-mobile, reduced-motion, Save-Data, fallback, reverse
   scroll, and remount checks are green.
9. The existing production mobile app remains unchanged.

---

## 12. Out of scope

- Rebuilding the full merchant application inside the landing page.
- Real authentication or merchant/customer records.
- Live payment, quote, invoice, schedule, upload, notification, or delivery calls.
- Making pricing, manifesto, or contact sections phone-driven when they describe no
  phone action.
- Changing the authenticated tablet/desktop application.
- Treating the landing replica as a reusable sandbox for every future app route.

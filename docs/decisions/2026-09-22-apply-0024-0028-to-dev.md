# Apply migrations 0024–0028 to the development database — owner decision

Date: 2026-09-22 UTC. Owner: Oliver. Execution lineage: `remediation/r1-continuation-20260907`.

## Why it was asked

Commit `662371ba` (originally `7ba8bc7d`) declares `users.session_version` (migration `0027`) in
`shared/schema.ts`. Drizzle's `select()` asks for every declared column, so every read of a
`users` row now asks for it. The development database (`workspace` target, host `helium`) has
migrations only through `0023`. Since the dev server restarted on this code (2026-09-22 05:58
UTC), password sign-in answers HTTP 500. `POST /api/auth/login` with a made-up email returns
`{"message":"Login failed"}` where 401 is expected. The same `SELECT` fails with
`column "session_version" does not exist` and succeeds without that column. Production is not
affected: it is offline by the owner's choice and not part of this decision.

## Question put, and the answer

> "Sign-in on the development app is broken (error 500) until its database gets the 5 pending
> changes (0024–0028). Apply them to the development database now?"

Options given: **"Yes, apply to development (Recommended)"**, described as "Development database
only; the live site is untouched. For the 2 invoice files, I use the ownership list exactly as the
tool drafts it from TaptPay's own records (your 21 Sept rule), with no edits. Then I confirm
sign-in works again and record your decision.", or "Not yet".

Answer: **"Yes, apply to development (Recommended)"**.

## What this authorizes

- A count-only run and a draft of the gap-13 upload-ownership inventory against the development
  database, using `db:draft-upload-inventory`. The draft is used **as drafted**: no entry is
  amended, and every owner or lock comes from the rule approved on 2026-09-21.
- `db:release` of `0024`–`0028` against the `workspace` target (`helium`), with that inventory and
  its SHA-256, after a dry run.
- The read-only checks around it: migration status, and the sign-in probe.

## What it does not authorize

Any migration against production or any other database. Deploying, or pushing. Editing the
inventory.

## Safety notes

- The encrypted operator backup (`docs/operations/encrypted-backup.md`) needs the owner's GPG
  recipient, and an unencrypted dump would breach that policy.
- `0024`, `0026` and `0028` only create tables, and `0027` adds one column with a constant
  default. `0025` is the only migration that changes existing rows: the owners of the 2 invoice
  documents. Their prior state (file ids and merchant ids, no paths or content) is recorded before
  the release, in the outcome below.
- Each migration runs in its own transaction, and the runner proves the end state (0 pending,
  drifted, orphaned or out-of-order).

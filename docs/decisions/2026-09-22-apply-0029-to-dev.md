# Apply migration 0029 to the development database — owner decision

Date: 2026-09-22 UTC. Owner: Oliver. Execution lineage: `remediation/r1-continuation-20260907`.

## Why it was asked

Commit `36a320d6` declares `push_subscriptions.user_id` (migration `0029`) in `shared/schema.ts`.
Drizzle's `select()` asks for every declared column, so every full read of a `push_subscriptions`
row asks for it. The development database (`workspace` target, host `helium`) stops at `0028`: a
read-only check found `user_id` absent, and a `SELECT` naming it fails with `column "user_id" does
not exist`. The dev server restarted at 07:23:29 UTC, on the tree of a session that crashed that
moment, and that tree already declared the column. So in the dev app, turning notifications on
fails and none are delivered. Every such read is caught, so nothing crashes. Production is not part
of this decision.

## Question put, and the answer

> "May I add the new notifications column to the development database (migration 0029)? It only
> adds one empty column and an index, the same way 0024–0028 were added this morning, and it fixes
> notifications in the dev app. Production is not touched."

Options given:

- **"Yes, apply it now (Recommended)"**: "I rehearse it first, apply it to the development
  database only, confirm the dev app can read notifications again, and record your decision."
- "Not yet": "The dev app's notifications stay broken until it's applied. Nothing else is
  affected."

Answer: **"Yes, apply it now (Recommended)"**.

## What this authorizes

- A dry run, then `db:release` of `0029` alone against the `workspace` target (`helium`).
- The read-only checks around it: migration status, the column and index present, the existing
  subscription rows unchanged apart from the new empty column, and the read that failed now
  succeeding.

## What it does not authorize

Any migration against production or any other database. Deploying, or pushing.

## Safety notes

- `0029` is additive. It adds a nullable column with no default (no table rewrite), a foreign key
  that every existing row satisfies (`NULL`), and one index. It changes no existing value. The
  dev table holds 2 rows.
- It runs in one transaction, and the runner proves the end state: 0 pending, drifted, orphaned or
  out of order.
- The encrypted operator backup (`docs/operations/encrypted-backup.md`) needs the owner's GPG
  recipient, and an unencrypted dump would breach that policy. The rows' prior state is recorded in
  the outcome instead.

# TaptPay — search, answer-engine and generative-engine optimisation plan (SEO · AEO · GEO)

Date: 2026-09-26. Written against `remediation/r1-continuation-20260907` @ `93aa6a0a` by reading the
code, not by running production. Every file:line below was true at that commit. Re-verify line
numbers before editing; they drift.

This plan covers every surface a search engine or AI assistant reads to answer a question about
TaptPay:
- the public marketing pages;
- their HTML heads, structured data, robots, sitemaps and headers;
- the served static files (PDFs, preview pages);
- the WooCommerce readme;
- off-site identity;
- measurement.

It is written to be executed by a coding agent in the Replit terminal, task by task, with a human
(Oliver, "You") answering the decisions only a human can make.

### 0.2 Rules inherited from the integration plan, restated because they bind here

1. **Fail first.** Where a task says so, capture the defect first: a failing test, or a
   `curl`/Playwright capture saved as evidence. Only then change the code.
2. **Never invent a convention.** Copy an existing pattern in this repo. Examples:
   - Jest projects: `npm run test:server` and `npm run test:client`.
   - Playwright scripts live under `scripts/`.
   - Decisions are one dated ADR each under `docs/decisions/`.
3. **Stage explicit paths only.** Never `git add -A` or `git add .`. Always exclude
   `.claude-home/**` and `.claude/settings.local.json`.
4. **No secrets or PII.** None in commits, evidence, screenshots or logs.
5. **Delete, don't flag.** A false claim is removed, not softened or hidden behind a toggle.
6. **Never edit an applied migration.** This plan needs **no** migrations. If a task seems to need
   one, that is a stop condition.
7. **Don't regenerate verifiers to go green.** Never hand-edit or regenerate a verifier, baseline,
   allowlist or golden screenshot just to turn it green. Landing-page visual changes need Oliver's
   approval (see the R1-H1 precedent).
8. **Things the agent never does:**
   - deploy;
   - change production visibility;
   - alter Replit Secrets;
   - edit DNS;
   - submit anything to Google, Bing, IndexNow, directories or review sites;
   - contact journalists or customers;
   - post on forums.

   Those are **You** tasks. The agent prepares the exact text and files for them.

## 2. What "top level" means here — and what nobody can promise

No-one controls Google rankings or whether an AI assistant cites a page. Anyone promising either is
guessing. What a first-class team controls, and what this plan does, in priority order:

1. **Machine access.** The site is public. Every important page returns its full content in the raw
   HTML response, identically to every client, fast, with correct status codes.
2. **Machine-readable truth.** Structured data, heads, PDFs and third-party listings say only true,
   current, consistent things. An AI engine repeats what it finds. Today TaptPay's
   machine-readable surface contains false statements (§3), and that is the most damaging SEO/GEO
   problem it has.
3. **Answer-shaped content.** Pages that each answer a real question directly, with specifics,
   sources and TaptPay's own original numbers. A retrieval system can lift a passage and quote it.
4. **Corroboration.** Independent sites (directories, partners, press, reviews, communities) say
   the same true things about the same entity. AI engines weight consensus across sources.
5. **Page experience.** Core Web Vitals at the 75th percentile:
   - LCP ≤ 2.5 s
   - INP ≤ 200 ms
   - CLS ≤ 0.1
6. **Measurement.** Search Console, Bing Webmaster Tools, crawler logs, AI referrals and a fixed
   prompt panel, reviewed monthly.

**Timeline.** A new domain in a competitive category (NZ payments/POS, rent collection,
trade invoicing) typically takes months, not weeks, to earn non-brand rankings. Brand queries
("taptpay") and AI answers about TaptPay itself are the fast wins. Category answers ("how do I take
card payments without an EFTPOS machine in NZ") are the long game.

### 2.1 Where each engine gets its answers (confidence labelled; re-check §G sources before relying on it)

| Engine | Index / fetcher it relies on | What that means for us | Confidence |
|---|---|---|---|
| Google Search, AI Overviews, AI Mode | Googlebot's index. Google states no special markup is needed for AI features; normal indexing and snippet eligibility apply. AI Mode "fans out" one question into many sub-queries. | Be indexable and snippet-eligible. Cover the sub-questions around each topic. `nosnippet`/`max-snippet` also limit AI-feature use. | High |
| Gemini app / Vertex grounding | Google data. The `Google-Extended` robots token controls use for Gemini training and grounding. It does **not** affect Search or AI Overviews. | Blocking Google-Extended costs Gemini-app visibility, not Search. | High |
| Microsoft Bing, Copilot | Bing's index. Supports IndexNow. Bing Webmaster Tools. | Bing indexing is mandatory. IndexNow speeds updates. | High |
| ChatGPT search | `OAI-SearchBot` (search), `ChatGPT-User` (user-triggered fetch), `GPTBot` (training). Also uses third-party search providers. | Allow OAI-SearchBot or you cannot appear. Being in Bing is also prudent. | High on bot names; medium on provider mix |
| Perplexity | `PerplexityBot` (index), `Perplexity-User` (user-triggered). | Allow PerplexityBot. | High |
| Claude | `ClaudeBot` (training), `Claude-SearchBot` (search), `Claude-User` (user-triggered). Web search has been reported to use Brave Search. | Allow Claude-SearchBot and Claude-User. The Brave dependency is unverified. | High on bots; **not certain** on Brave |
| Apple (Siri, Spotlight, Safari suggestions) | `Applebot`. `Applebot-Extended` controls model-training use only. | Allow Applebot. | High |
| Many LLMs' training data | Common Crawl (`CCBot`) and vendor training crawlers. | Allowing training crawlers on marketing pages raises the chance a model "knows" TaptPay without searching. | Medium (inference) |

Consequences that drive this plan:

- **Most AI fetchers do not run JavaScript.** Vercel's December 2024 analysis of AI-crawler traffic
  reported that GPTBot, ClaudeBot and PerplexityBot do not execute JavaScript. Treat this as
  reported, and confirm it in our own logs (S6-T1). TaptPay's body content is client-rendered only
  (F8), so today these bots see an empty page plus the (false) head.
- **Google and Bing indexes cover most AI surfaces.** Every task that improves normal indexing
  improves AI visibility too.
- **GEO evidence is thin.** The most cited study, *GEO: Generative Engine Optimization*
  (Aggarwal et al., arXiv 2311.09735, KDD 2024), found that in their benchmark three things raised
  visibility in generated answers: adding cited sources, quotations and statistics. Keyword stuffing
  did not help. That is a benchmark, not a production engine. We adopt its low-risk findings
  (sources, specific numbers, quotable sentences) as writing rules (§7.3), not as guarantees.
- **llms.txt is not a ranking factor.** No major engine has confirmed it reads it, and a Google
  representative has said Google does not. It costs about an hour, so S2-T8 builds it as a
  labelled hedge, generated from the same source so it cannot drift.

## 5. Target architecture

### 5.1 Principle

Marketing pages are **static HTML generated at build time**. Content pages ship with **no React
hydration**. The landing page ships as static markup plus its existing imperative runtime as a
script ("island"). Every client, crawler or human, gets the same bytes. The logged-in app stays
the SPA.

Rejected alternatives:
- **User-agent-based "dynamic rendering"** (what F7 half-does). Google calls it a workaround, and
  per-UA HTML is fragile.
- **Full SSR or a framework migration** (Next.js etc.). Large blast radius during a security
  remediation, for no marketing benefit over static HTML.

### 5.2 Why this fits the existing code

- `client/src/pages/landingRuntime.ts` imports only `three`, no React (verified). It drives the page
  by querying element ids. `LandingPage` is pure markup plus a `useEffect` that loads the runtime.
  Effects don't run during server rendering, so `renderToStaticMarkup(<LandingPage/>)` produces the
  full markup, and a small entry script can start the runtime.
- Vite 5.4 is already the bundler (`vite.config.ts` root `client`, outDir `dist/public`). Vite's
  documented SSR build (`vite build --ssr <entry>`) bundles the page components, including CSS
  imports, into a Node-importable module. A prerender script then writes HTML files. That is Vite's
  own pre-rendering pattern.
- No new runtime dependencies. `react-dom/server` ships with `react-dom` 18. `tsx` is a
  devDependency that the deploy already installs (`replit.md` line 82).

### 5.3 Build pipeline (the `build` script becomes)

```text
vite build                                   # client SPA + new landing-entry, with build.manifest: true
&& vite build --ssr src/marketing/entry-server.tsx --outDir ../dist/marketing-ssr
                                             # (paths resolve against Vite root = client/;
                                             #  confirm on the first run)
&& tsx scripts/marketing/prerender.ts        # writes dist/site/**/index.html, sitemap.xml,
                                             #   robots.txt body, llms.txt, og images manifest
&& esbuild server/index.ts ...               # unchanged
```

- `dist/site/` is separate from `dist/public/`. Writing the landing page to
  `dist/public/index.html` would replace the SPA shell, and the SPA fallback would then serve the
  landing page for every app route.
- The prerender reads Vite's manifest (`dist/public/.vite/manifest.json` in Vite 5) to find the
  hashed `landing-entry` JS and CSS.
- **Origin:** the prerender uses `SITE_ORIGIN` from `client/src/marketing/site.ts` (the D-SEO-2
  constant). If `PUBLIC_ORIGIN` is set at build time and differs from it, **the build fails**. It
  never guesses.

### 5.4 Request handling (new `server/seo/` module, mounted in `server/index.ts` before `serveStatic`)

**1. Marketing pages.** `GET`/`HEAD` on a path in `dist/site/manifest.json` gets
`dist/site/<path>/index.html`:
- `200`, `Content-Type: text/html; charset=utf-8`;
- `Cache-Control: public, max-age=300, must-revalidate`, plus ETag.

Canonical URLs have no trailing slash. `/pricing/` 301s to `/pricing`, but `/` stays `/`.

**2. `robots.txt`, `sitemap.xml`, `llms.txt`, `llms-full.txt`, `<indexnow-key>.txt`.** Served from
`dist/site/`. The `/robots.txt` and `/sitemap.xml` handlers are **removed** from `routes.ts`.

**3. App (SPA) routes.** Paths matching `client/src/marketing/app-route-patterns.ts` get the SPA
shell with `X-Robots-Tag: noindex`.
- Exception: `/login` and `/signup` stay indexable, with server-injected per-route
  title/description/canonical. The injection is identical for every user agent.
- `app-route-patterns.ts` is a new list that a client test keeps in sync with every
  `<Route path=…>` literal in `App.tsx`, including the routes the `RouteTable` components define
  (`App.tsx:~778-809`). App.tsx itself is not edited.

**4. Bearer-token routes** (`/pay/t/`, `/checkout/t/`, `/receipt/t/`, `/split/t/`, `/r/`,
`/trades/quote/`, `/pay/return/`, `/accept-invite`, and legacy `/pay/:id`, `/checkout/:id`,
`/receipt/:id`, `/split/:id`, `/payment/result/:id`):
- `X-Robots-Tag: noindex, nofollow, noarchive`.
- **Not** disallowed in robots.txt. A leaked URL must stay crawlable so the crawler sees
  `noindex` and drops it.

**5. Static files** under `client/public`:
- hashed `/assets/*`: `Cache-Control: public, max-age=31536000, immutable`;
- `/app/*.html`, `/hpp-preview.html`, `/app/hpp-preview.html`: `X-Robots-Tag: noindex`;
- PDFs: keep indexable only if S0-H2 approves their content; otherwise `noindex` or remove.

**6. Unknown paths:** real **404** with the SPA's NotFound shell and `X-Robots-Tag: noindex`.

**7. Non-canonical hosts** (`*.replit.app`, `*.replit.dev`, `*.repl.co`, any host ≠ `SITE_ORIGIN`'s
host):
- add `X-Robots-Tag: noindex` to HTML responses;
- **no redirect**. Webhooks, return URLs or the iOS shell may still use those hosts; redirecting
  them is a remediation-lane decision.
- Use `req.headers.host`, not `req.hostname`. `trust proxy` belongs to R1-T4 phase B.

### 5.5 Content model (`client/src/marketing/`)

Content is typed TypeScript modules, not Markdown. That means no new parser dependency, `tsc`
checks it, and it follows the repo's typed-module convention.

```text
client/src/marketing/
  site.ts                  SITE_ORIGIN, brand name, org identity (from D-SEO-7), nav, footer
  claims.ts                claims register (see 5.6)
  app-route-patterns.ts    SPA route patterns (kept in sync with App.tsx by test)
  schema/                  JSON-LD builders (Organization, WebSite, WebPage, Breadcrumb,
                           SoftwareApplication+Offers, FAQPage, Article, DefinedTermSet, VideoObject)
  templates/               Layout, Header, Footer, AnswerBlock, FactsTable, Steps, FAQ,
                           Sources, AuthorBox, Breadcrumbs, CTA, ComparisonTable
  pages/                   one module per URL: export const page: MarketingPage
  entry-server.tsx         renders a page by path → { html, head, jsonLd }
  types.ts                 zod schema for MarketingPage
```

`MarketingPage` fields, validated with zod at build:
- `path`, `title` (≤ 60 chars target), `description` (≤ 155 target), `h1`;
- `answer`: the 40–60-word direct answer shown first;
- `type`: `home | pricing | vertical | feature | guide | compare | glossary | about | legal | faq`;
- `faq[]`: question and answer, rendered visibly;
- `claims[]`: claim ids used on the page;
- `sources[]`: title, url, publisher, accessed date;
- `author`, `reviewedBy?`;
- `datePublished`, `dateModified`: set by hand on substantive change only;
- `ogImage`, `breadcrumbs`, `related[]`: internal links;
- `body`: a React component using the templates.

### 5.6 The claims gate (truthfulness enforced by the build)

`claims.ts` is the single register of every factual statement about TaptPay that appears on any
public surface: pages, JSON-LD, llms.txt, the Woo readme, PDFs, OG text. Each claim has:
- `id`, `text`;
- `status: verified | owner-attested | unverified | false`;
- `evidence`: a code path plus flag state, an ADR, a contract reference or a primary-source URL
  with accessed date;
- `reviewBy`: a date.

The build and `seo:verify` fail if:
- a page cites a claim that is not `verified` or `owner-attested`;
- a JSON-LD field that encodes a capability or price comes from anywhere but a claim or
  `shared/plans.ts`;
- a claim's `reviewBy` has passed;
- banned phrases (`lowest`, `cheapest`, `#1`, `best`, `guaranteed`, `instant`, `100%`) appear in
  page text without a claim id backing them.

### 7.2 Page anatomy (every commercial and guide page)

1. **H1** = the question or topic in the user's words.
2. **Answer block**, directly under the H1: 40–60 words that fully answer the question in plain
   sentences. The first sentence names the entity, e.g. "TaptPay is …" or "In New Zealand, …".
   This is the passage featured snippets, voice answers and AI engines lift.
3. **Key facts table:** price, what's included, who it's for, requirements — with numbers.
4. **Body:** H2s that are the fan-out sub-questions, each opening with a 1–2 sentence answer.
   Each section is self-contained: repeat the entity name, not "it", so a retrieved chunk makes
   sense on its own.
5. **Steps list** where there's a process. A numbered `<ol>`, not prose.
6. **Worked example with TaptPay's own numbers:** information that isn't available elsewhere.
7. **FAQ:** 3–6 visible Q&As, marked up.
8. **Sources:** primary sources linked (IRD, Commerce Commission, Tenancy Services, Windcave docs,
   the competitor's own pricing page), each with an accessed date.
9. **Author box** (+ reviewer if D-SEO-8 applies), plus a visible **"Last updated <date>"**.
10. **CTA:** signup or contact.
11. **Related links:** 3–6 internal links with descriptive anchor text (never "click here").

### 7.3 Writing rules (for the agent drafting and for Oliver approving)

- **Truth first.** Every factual sentence about TaptPay maps to a claim id. Every factual sentence
  about the world maps to a source. If neither exists, delete the sentence.
- **Specific over vague.** "Collecting $2,400 rent costs $7.20 in TaptPay fees" (if D-SEO-4 makes
  it true, and stating what is excluded) beats "low fees".
- **Quotable sentences.** One idea per sentence. Definitions in "X is Y that Z" form. Numbers with
  units and currency ("NZ$7.99 a month, excl. GST", per D-SEO-4).
- **Consistent entity naming.** "TaptPay" in every running-text first mention per section; never
  "Tapt".
- **Match the query's language.** NZ English and NZ terms (EFTPOS, tradie, flatmate, bond, IRD,
  GST), not US terms.
- **Neutral guides.** Guides include non-TaptPay options fairly. A guide that is an ad doesn't get
  cited, and damages trust.
- **No hidden text, cloaking, doorway pages, AI-spun duplicates or keyword stuffing.** Each is a
  spam-policy violation.
- **Freshness is real or absent.** `dateModified` changes only when facts change.
- **Accessibility counts:** alt text, heading order, link text. It is also how machines parse
  structure.

- Anything requiring deploy, production visibility, DNS, Replit Secrets, an external submission,
  outreach or posting.
- The build cannot produce `dist/site` without network access or secrets.
- A remediation-lane merge conflicts with SEO changes in `server/index.ts` or `server/vite.ts`:
  stop and ask which side wins. Never resolve security code in SEO's favour.

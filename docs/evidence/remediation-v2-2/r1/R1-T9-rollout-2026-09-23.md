## The pattern, applied per screen

- A request counts as **unavailable** only when it failed with nothing loaded yet:
  `query.isError && query.data === undefined`. A failed background refresh keeps what is shown.
- The screen's main figure is replaced in its own frame by `DesktopLoadFailure` (one
  `role="alert"` per failure, Try again). Lists and secondary figures say so in quiet text.
- Actions that need the missing data are off, with a tooltip saying why. Actions that do not
  need it stay available.
- A secondary source that failed says "unavailable", never a zero.
- Loading and loaded views do not change.

Each screen: tests first (red on `e4c25fb1` for the stated reason), then the change, then a
mutation check (each fix undone in turn, the tests must fail), then screenshots from a build of
`e4c25fb1` and a build of the change, captured in one run.

### The screenshot check, made repeatable

Before trusting a comparison, the same build was captured twice. It differed:

1. 2858 pixels on the stock cards: their entrance animation had not settled. Screenshots now
   finish animations first (`animations: "disabled"`).
2. 13 pixels along the analytics chart's line: the chart is drawn against the live clock, which
   moves between captures a few seconds apart. The page clock is now fixed for the whole run
   (`page.clock.setFixedTime`); the fixtures' dates are relative to the same moment.
3. 3 pixels one shade apart in a gradient. The check now fails on pixels that differ by more
   than 2 in a channel, and prints both counts.

After that the same build captured twice matched on every screen. Two *different* builds still
differed on retail analytics, whose code is byte-identical in both (the chart's edge, then the
highlighted tab under reduced motion): the builds split their code differently, so the page
settles at a slightly different moment. Captures now use reduced motion (the app draws every
entrance settled), and `R1T9_SCREENS` runs only the screens a change touches. A zero from this
check proves nothing changed; a non-zero on an untouched screen can be timing.

Then, for property analytics, a sub-pixel shift of the top bar's tab highlight and one button's
outline still failed a raw count, including between two captures of one build. Since `5805a416`
the check uses Playwright's own screenshot comparison (what `toHaveScreenshot` uses: pixelmatch,
ignoring anti-aliased pixels), with the raw count printed beside it. Sanity check: it matches
identical code, and flags the loaded against the failed view of the terminal (8,072 pixels) and of
stock (90,084 pixels). On that run all six captured screens matched their `fafc6598` builds.

## The pattern, applied per screen

- A request counts as **unavailable** only when it failed with nothing loaded yet:
  `query.isError && query.data === undefined`. A failed background refresh keeps what is shown.
- The screen's main figure is replaced in its own frame by `DesktopLoadFailure` (one
  `role="alert"` per failure, Try again). Lists and secondary figures say so in quiet text.
- Actions that need the missing data are off, with a tooltip saying why. Actions that do not
  need it stay available.
- A secondary source that failed says "unavailable", never a zero.
- Loading and loaded views do not change.

Each screen: tests first (red on `e4c25fb1` for the stated reason), then the change, then a
mutation check (each fix undone in turn, the tests must fail), then screenshots from a build of
`e4c25fb1` and a build of the change, captured in one run.

### The screenshot check, made repeatable

Before trusting a comparison, the same build was captured twice. It differed:

1. 2858 pixels on the stock cards: their entrance animation had not settled. Screenshots now
   finish animations first (`animations: "disabled"`).
2. 13 pixels along the analytics chart's line: the chart is drawn against the live clock, which
   moves between captures a few seconds apart. The page clock is now fixed for the whole run
   (`page.clock.setFixedTime`); the fixtures' dates are relative to the same moment.
3. 3 pixels one shade apart in a gradient. The check now fails on pixels that differ by more
   than 2 in a channel, and prints both counts.

After that the same build captured twice matched on every screen. Two *different* builds still
differed on retail analytics, whose code is byte-identical in both (the chart's edge, then the
highlighted tab under reduced motion): the builds split their code differently, so the page
settles at a slightly different moment. Captures now use reduced motion (the app draws every
entrance settled), and `R1T9_SCREENS` runs only the screens a change touches. A zero from this
check proves nothing changed; a non-zero on an untouched screen can be timing.

Then, for property analytics, a sub-pixel shift of the top bar's tab highlight and one button's
outline still failed a raw count, including between two captures of one build. Since `5805a416`
the check uses Playwright's own screenshot comparison (what `toHaveScreenshot` uses: pixelmatch,
ignoring anti-aliased pixels), with the raw count printed beside it. Sanity check: it matches
identical code, and flags the loaded against the failed view of the terminal (8,072 pixels) and of
stock (90,084 pixels). On that run all six captured screens matched their `fafc6598` builds.

Unlike property's payments, a trades invoice carries no client name: the history gets its names
from the clients request. Its existing fallback, "Job payment", is meant for a payment whose client
row is missing; with the whole request failed it was on every row. The rows stay (their amounts,
dates and statuses come from the payments), and a quiet line with a retry says what is missing:
the pattern the property terminal uses for its schedules list.

**Reports and exports only from loaded data.** Mapping the actions found two more ways a report
or export could be made from data that was not there. Both start with a click while the page is
still loading (Reports and Export are live then; the design keeps loading views unchanged):

- **Generate Report** while a request was still loading built the report from the empty
  fallbacks. The in-page report fills in when the data arrives, but if the request failed instead,
  it stayed at $0 with no alert: the overview, where the alert sits, is hidden while a report is
  shown. Generate now stays off until all three sources have loaded.
- **Export** clicked while loading opened the export dialog at once. If the load then failed, the
  dialog stayed open and would make a PDF or CSV from no payments. The dialog now opens once the
  data has loaded; if a source fails first, the request is dropped, so it does not pop up after a
  later Try again. (Surfacing the failure inside the dialog was not an option: its only error
  display is red.)

## Reports and exports only from loaded data — `0c75e747`, `d5cf4d5f`, `88fe0e3f`, `721ce328`

The rule found on trades analytics, applied to all three analytics screens: a report or export is
made only from data that has loaded. Each waits for exactly the sources it is built from, off with
a tooltip naming the missing one; a report picked or an export asked for while a source is still
loading waits for it; an export asked for before a failure is dropped (it does not pop up after a
later retry).

| Screen | Reports (on screen) wait for | Export waits for |
|---|---|---|
| Trades analytics | payments, clients, quotes | the same, and the business details (header; GST mode) — `0c75e747` |
| Property analytics | payments, tenants, rent schedules | the same, and the business details (header; GST line) — `d5cf4d5f` |
| Retail analytics | the sales; Stock Performance also the products, Revenue by Board the boards, GST & Tax Summary the business details — `721ce328` | the sales and the business details |

The business details are in every export's header, and decide GST: trades' GST mode, property's
GST line. Before `707cff2f` they never loaded after a password sign-in, so an export waiting for
them would have stayed shut for those merchants; that fix came first
([evidence](R1-T9-export-business-details-2026-09-23.md)).

Retail's reports differ in what they need, so only the three that need more than the sales wait:
with the boards failed, Revenue by Board is off and the other nine stay available
([boards failed, Reports open](r1-t9-rollout-2026-09-23/retail-analytics-boards-failed-reports-after.png));
with the business details failed, Export and the GST & Tax Summary are off
([after](r1-t9-rollout-2026-09-23/retail-analytics-business-details-failed-after.png)). What each
of those three read a failure as, before: Revenue by Board put every sale under "Unassigned",
Stock Performance listed no unsold products, and the GST & Tax Summary said "gst collected"

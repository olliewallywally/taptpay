## Design

1. **Principal contexts.** Signed out; a token that is invalid or expired; the owner; a teammate; a
   disabled teammate; another business's owner; the platform admin; and, on the routes that take
   them, a cron secret, a provider callback, an ecommerce API key and a bearer token (right and
   wrong).
2. **The matrix, recorded** (`server/route-matrix.ts`): per route, derived from its review (who each
   branch admits) plus the P2.2 answer for every refused context; rendered into the inventory table.
   A test fails when a route has no row, or when the matrix and the review disagree.
3. **The runtime matrix test**, per API row: a recipe (fixtures and a request the allowed principal
   succeeds with), then every context: allowed → its success status; refused → the matrix's status,
   the storage snapshot unchanged, nothing sent (fetch, email, SMS, push, events). Built family by
   family, as R1-T2's reviews were: (a) the P2.2 fixes and the matrix framework; (b) signed-out,
   cron, provider, API-key and bearer routes; (c) the account and settings; (d) sales, refunds and
   reports; (e) property; (f) trades; (g) admin. The property and trades fakes move to shared test
   support.
4. **Client guards:** a router-level test per listed route, per context, per shell (phone, desktop):
   signed out → `/login?returnTo=…`; owner and teammate → the page; another business's record → the
   page's not-found; admin (separate token) → per the guard. Hook order checked by rendering each
   path through `App`'s router.

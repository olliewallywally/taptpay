## R1-H1 — D10 device gate

Defect: `client/src/hooks/use-device-class.ts`'s `classifyDevice` returned
`"mobile"` for any viewport with `Math.min(width, height) < 700`, with no
pointer gate on that clause. A fine-pointer (non-touch) desktop browser
resized short — 1440×650 is the plan's own example — fell into the phone UI
purely on height.

Fix: the short-side mobile check is now skipped when the pointer is fine and
width already qualifies as desktop-class (≥1024px); touch/coarse-pointer
classification is untouched, and narrow fine-pointer windows (390×844) still
classify as mobile. See `docs/decisions/2026-09-06-D10-device-gate-fine-pointer-short-window.md`
for the full decision record.

Regression: `client/src/__tests__/use-device-class.test.tsx` — the
`[1440, 650, false]` case was an *asserted* `"mobile"` (the bug, encoded as
correct) before this change; flipped to `"desktop"`, proven red against the
unmodified hook, then green after the fix. All nine other cases in that table
are unchanged and still pass.

**Owner acceptance of this baseline commit and the D10 ADR is still needed —
R1-H1 is a "You" task per the plan.** T4, T8 and T10 are blocked on it.

## R1-T1 — no-live-system HTTP test harness

New: `server/__tests__/support/test-env.ts` (deterministic env, forces
MemStorage regardless of the ambient dev DATABASE_URL), `server/__tests__/support/http-harness.ts`
(builds the real `registerRoutes(app)` + `createGlobalErrorHandler()` app with
no listener/Vite/migrations/seed/cron, plus fixture principals), and
`server/__tests__/http-harness.test.ts` (the first runtime HTTP test in this
repo — the existing 30 server tests are all source-text/unit-level, per
`token-route-inventory.test.ts`'s and `subscription-route-security.test.ts`'s
pattern of grepping `routes.ts` as a string).

Fixtures implemented and exercised: `merchantAOwner`, `merchantAMember`,
`merchantBOwner`, `disabledUser`, `validatedAdmin`, `cronCaller`. Implemented
but not yet exercised by a test: `ecommerceApiKey` (header shape only —
`FEATURE_ECOMMERCE_API` is off by default so the fixture proves the 404-before-key-check
ordering, not a real key lookup), `publicPaymentBearer`/`providerNotification`
(the plan itself frames these as non-account credentials, not JWT principals —
`mintPaymentCredential()` exposes the raw/hash pair for a future payment-flow
test to attach to a transaction it creates; there is no route sending an
unauthenticated provider notification test yet, that is R2/R3 scope).

### Two real defects found and fixed while building this (blockers, not the harness's job to work around)

1. **`server/routes.ts:399` used `import.meta.dirname`.** ESM-only syntax;
   `jest.server.config.cjs` compiles the server project to CommonJS via
   ts-jest, so no test file could ever `import` (or transitively load)
   `server/routes.ts` — a hard blocker for R1-T1's entire premise. Replaced
   with `process.cwd()`-based resolution, matching the existing convention
   (`auth.ts`'s log directory) and `server/migrate.ts`'s comment already
   documenting this exact CommonJS constraint. Behaviourally identical: the
   process always runs from the repo root in dev/production/test. Regression
   test added (`http-harness.test.ts`'s Apple Pay domain-association case).
2. **Two `setInterval` timers without `.unref()`** (`server/routes.ts:267`
   rate-limit cleanup, `server/routes.ts:7059` trades token-rate cleanup)
   kept the process alive indefinitely after a test run completed — Jest
   printed "did not exit one second after the test run" and the process had
   to be killed. `.unref()` added to both, matching `auth.ts`'s
   `loginAttemptCleanupTimer` — zero behavioural change to a running server
   (which never intentionally exits), pure process-lifecycle correctness.

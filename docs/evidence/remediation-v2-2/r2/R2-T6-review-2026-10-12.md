# R2-T6 §21.1 review — test matrix, logging guard and R2 exit, 2026-10-12

Reviewed: plan §9.6 (cases and exit criteria), the R2 preflight (RF-6, call-site table),
the [owner direction](../../../decisions/2026-10-12-r2-t6-proceed-owner-direction.md), and
`server/windcave.ts`, `server/windcave-client.ts`, the provider routes in `server/routes.ts`
and `server/subscription-billing.ts` / `subscription-cron.ts` at `1359e646`. Both passes by
this session; the independent R2 review remains owed with the owner's R1–R2 review.

## Pass 1

### Verification of Prior Fixes
Re-derived from the tree, not from the T1–T5 evidence: the retail, numbered and invoice
session creation and queries go through the T1 client, T2 link validation, the T3 parser
and the T5 verifier. `legacyFailure` carries no provider text. The retail token routes log
fixed messages only.

### Blocking Issues
1. **RF-6 is open.** Provider reply text (up to 200 characters, or all of it for Google
   Pay and refunds) is returned in `error` strings by the stored-card, Google Pay, refund
   and Tap to Pay functions; `subscription-cron.ts` logs a failed charge's `error`. The
   numbered notification and callback, and the rent and trades notifications, log the
   provider session ID, and two log the raw query and body.
2. **The card-on-file flow bypasses R2's allowlisting** (preflight gap: the call-site table
   listed it, no slice covered it). `createCardStorageSession` returns the `hpp` link, or
   else any `REDIRECT` link, to the browser unvalidated, and sends callback addresses
   without checking their origin (RF-4 for card setup). R2's exit ("no provider URL or
   query result can bypass strict parsing/allowlisting") fails while this stands.
3. **Redirects are followed.** Both transports use `fetch`'s default `redirect: "follow"`;
   a 3xx from the provider endpoint would be followed. §9.6 lists "redirect" as a case.

### High-Risk Concerns
1. The stored-card read-back trusts `transactions[0]` and does not compare the returned
   session ID (one repository fixture returns a different ID from the one queried). A
   stored-card charge's reply is accepted on `authorised` alone, with no amount, currency
   or reference check. The fixtures omit those fields, so requiring them is a guess about
   the live shape that could stop renewals: checked when present, required only on the
   owner's word after UAT (owner direction).
2. Removing session IDs from logs costs support correlation. The internal sale or invoice
   ID is logged instead, which support can map to the session from the database.

### Missing Steps
A runtime guard: drive every provider function and provider route with marker values
(session ID, reply text, wallet token, X-ID) and assert none appears in any log line or
browser response. A §9.6 matrix test through the real client, wrapper, parser and
verifier with official-shape fixtures, each case named. The R2 exit record.

### Unsafe Assumptions
That a JSON parse failure cannot carry reply text into a log: the T1 client returns
`malformed` without throwing, and the stored-card functions catch their own parse; the
guard test covers this.

### Required Ordering Changes
Failing tests first: the guard and matrix tests are written before the fixes and shown red.

### Open Product / Provider / Legal Questions
Whether stored-card replies must carry the session ID, amount, currency, reference and
type (owner direction). Whether a provider decline text ("INSUFFICIENT FUNDS") may stay in
the merchant's billing history: it is the provider's short response text, shown today; not
changed here.

### Compliance and Data-Handling Notes
Logs keep categories, statuses and internal IDs only. No marker value, real ID or provider
text in tests or evidence.

### Test and Rollback Adequacy
Adequate with the guard, the matrix, the existing stored-card contract tests updated only
where a fixture's session ID was inconsistent, and full suites. Rollback is a code revert.

### Final Recommendation
**Approve** R2-T6 as scoped: RF-6 closed in `windcave.ts`, the provider routes and the
subscription cron; card-setup link and callback validation; no followed redirects;
stored-card replies checked when the fields are present; the §9.6 matrix and log guard; the
R2 exit record with residuals named. Tap to Pay (R7) and refunds (R4) stay off; their
error strings are cleaned but their flows are not otherwise changed.

## Pass 2 (recorded reread)

- `redirect: "manual"` returns the 3xx to the caller (Node's fetch), which the client then
  treats as an unexpected status: unknown, never approved or declined. A redirect on
  session creation is "the provider may have accepted", so the caller's X-ID retry logic
  is unchanged.
- The stored-card read-back's session check must not refuse the 202 "still pending"
  reply, which carries only an ID.
- The card-setup route already refuses a result without `hppUrl` (502), so a rejected link
  is a failed setup the merchant can retry, not a stuck one.
- No new blocking issue. **Approve** stands.

## Pass 3 (implementation reread, after the code and tests)

- **Scope added:** plan §9.4's last reconciliation code and time. The R2-T4 ADR said R2-T5
  would write 0034's two reconciliation columns; it did not. Written now on every retail
  provider query, sanitized codes only, the two columns alone, and never blocking a
  payment; checked on PostgreSQL 16 through `DatabaseStorage`. No new product decision:
  the plan requires it and the columns exist. Approve.
- **Not added:** plan §9.4's unique index on the processor X-ID, also missing from the

  (exit record R-4/O-5).
- Two stored-card fixtures were not Windcave's documented shapes and are corrected; the
  code they tested accepted both shapes, which is the gap this slice closes.
- The log guard's module cases check each result's `error` text, not its data fields: a
  provider transaction ID is stored by callers (it is the settlement's identity), not
  logged.
- No new blocking issue. **Approve** stands.

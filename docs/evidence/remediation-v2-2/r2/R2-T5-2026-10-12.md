## Found while implementing

1. **Gap 11's cross-share half, closed.** A numbered split sale keeps its session bound and
   `finaliseHostedPayment` returns it to `pending` after each share. A payer re-posting the
   completion, the provider's notification for that session, or the browser's return each
   queried the same approved session again and counted the **next** share: one payment
   could mark every share paid. Shown red on `6f1a67e2` and green now
   (`r2-t5-split-share-replay.test.ts`): the next share's reference differs from the one the
   session carries, so the repeat is a mismatch and counts nothing (it records a
   `PROVIDER_OUTCOME_MISMATCH` event, field `reference`). An unsplit sale's repeat is still
   re-settled (counted and pushed again): gap 11's remainder, R3 (C20).
2. **A regression avoided.** With RF-3 fixed, a duplicate-request reply carries no
   approval; the numbered `/pay` and invoice session routes settled from that field and
   would have recorded every such sale as failed and every such invoice as declined. Both
   now settle nothing.
3. **Supersedes an R2-T4 note.** R2-T4's evidence said attempts claimed before 0034 must be
   "cannot verify". T5 instead verifies them against the values their session was opened
   with (review pass 2): the same reference (`TAPT_<attempt>`) was already sent before
   T4, and treating them as unverifiable would strand every attempt in flight when 0034 is
   applied. For the owner's review.

## For the owner (R1–R2 review)

- **UAT check (owner direction):** whether Windcave reports an abandoned or cancelled card
  page as a complete session with no transaction. Today that stays "being checked".
- **Payer message:** on a 503 "still being reconciled" the numbered and invoice pages show
  "Something went wrong. Please try again.", which invites a second payment while the
  first is being checked. Before T5 the same case said "Payment was declined" (and
  recorded a decline), so the risk is not new; a "we're checking your payment — don't pay
  again" state is a product/UX change, left for the owner (R3's reconciliation).
- **A numbered split sale's concurrent payers** were already limited by R1-T7's binding
  (each `/pay` rebinds the sale's one session); T5 adds that a session opened for one share
  can only count that share.

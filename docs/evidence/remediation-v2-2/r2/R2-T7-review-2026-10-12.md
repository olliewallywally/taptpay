## Pass 1

### Verification of Prior Fixes
Re-derived: 0022 created `payment_attempts_processor_session_id_uq`; 0034 created
`payment_attempts_provider_transaction_id_uq`; nothing indexes `processor_x_id`. Both
storage implementations refuse a duplicate session ID, X-ID or return state at attach with
a read-then-write check; two concurrent attaches can both pass it.

### Blocking Issues
None.

### High-Risk Concerns
1. A duplicate in live data would make the index build fail. The migration checks first
   under a SHARE lock and aborts with counts only, performing no remediation (as 0022).
2. A race lost at the index would surface from `DatabaseStorage` as an unhandled
   unique violation (a 500 after the provider session exists). The attach now answers it
   as a conflict, like finalize does for 0034's index.

### Missing Steps
A PostgreSQL rehearsal: refusal on duplicates without printing them, clean apply with
nulls allowed, baseline contract, refusal of an existing index, a direct duplicate
refused, and a deterministic attach race reaching the index.

### Unsafe Assumptions
That the retail X-ID (16 hex characters of the attempt's UUID) cannot collide. About 60
random bits makes it improbable, not impossible; the index makes it impossible.

### Required Ordering Changes
0035 after 0034 (the T4 verifier no longer assumes 0034 is the newest).

### Open Product / Provider / Legal Questions
None; applying it is the owner's step.

### Compliance and Data-Handling Notes
The migration's refusal names no X-ID (R2-T6's rule that provider identifiers stay out of
logs); the runner already withholds the driver's message.

### Test and Rollback Adequacy
Schema and migration-list tests failing first; the PostgreSQL verifier; full suites.
Rollback is a code revert; the index may stay.

### Final Recommendation
**Approve** 0035 and the attach conflict handling as repository work, applied nowhere.

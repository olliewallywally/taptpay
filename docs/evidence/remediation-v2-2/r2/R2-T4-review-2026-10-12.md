# R2-T4 §21.1 review — expected provider values, 2026-10-12

Reviewed: the [schema ADR](../../../decisions/2026-10-12-r2-t4-expected-values-schema.md)
and the [owner direction](../../../decisions/2026-10-12-r2-t4-proceed-owner-direction.md),
against plan §9.4, §10.1 and §10.6, at `f0578517`. Both passes were performed by the
session that wrote the ADR; the independent R2 review remains owed.

## Pass 1

### Verification of Prior Fixes
T1–T3 are implemented and pushed (`8bca01cc`, `956e74d4`, `a044533e`), with their
evidence re-derived from the commits rather than from the record. The R2-T3 parser
already yields integer cents, currency, reference, transaction ID and session ID for
the verifier to compare.

### Blocking Issues
None for repository work. Applying `0034` anywhere is outside this scope.

### High-Risk Concerns
1. In-flight attempts at deploy: attempts claimed or attached by the old code have no
   expected values. Nullable columns plus code-level ordering keep them working; T5's
   verifier must treat a missing expected record as "cannot verify, reconcile", never
   as a pass.
2. The partial unique index on `provider_transaction_id` turns a second attempt
   claiming the same provider transaction into a constraint error inside finalization.
   It must surface as a conflict, not a crash or a silent success.

### Missing Steps
Count-only preflight queries for the production rehearsal (rows, live attempts
without expected values, any non-null provider transaction IDs); the local rehearsal
script; the migration list pin in `migrate.test.ts`.

### Unsafe Assumptions
That `paymentAmount` in the retail route is a canonical decimal string; T4 converts it
with T3's `parseCentsExact` and refuses the request if it is not.

### Required Ordering Changes
Route order: provider configured → record expected values → create session → attach.

### Open Product / Provider / Legal Questions
None new. Preflight Q1/Q3 are not needed for T4.

### Compliance and Data-Handling Notes
The merchant reference stored is `TAPT_<attempt UUID>`, already sent to the provider;
no customer data is added. No evidence file holds a real reference or ID.

### Test and Rollback Adequacy
Adequate if tests cover: record/idempotent/conflict/after-attach refusal, attach
refused without expected values, provider transaction ID stored at finalize, the
duplicate-transaction conflict, MemStorage and PostgreSQL parity, and a from-zero
migration rehearsal. Rollback is a code revert; the columns can stay.

### Final Recommendation
**Approve** R2-T4 as repository work and a local rehearsal on `ccr-e07e3100-0wm8kr` from
`f0578517`. Not approved: applying `0034` to any shared database.

## Pass 2 (recorded reread)

- Rechecked the deploy overlap the other way round: new code finalizing an attempt
  whose session the old code attached. Finalization does not require expected values,
  so it still completes; only T5's verifier will refuse to call such an attempt
  verified. Consistent with concern 1.
- Rechecked that the all-or-none CHECK cannot fail on existing rows (all four columns

- Rechecked that the route records expected values only after the provider is known to
  be configured, so a disabled provider writes nothing.

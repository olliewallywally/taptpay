## Pass 1

### Verification of Prior Fixes
T1–T4 re-derived from the tree: the session client, link validation, strict parser and
exact cents exist; `payment_attempts` carries expected values from T4. Re-read at this
commit, the numbered card completion settles `queryResult.approved === true` without
checking `success`, so a timeout or any unknown result is recorded as a decline: a new,
worse instance of RF-2.

### Blocking Issues
None, given the owner direction's choices for the legacy flows and references.

### High-Risk Concerns
1. Strictness strands abandoned or cancelled card pages as "being checked" (owner
   direction, consequence). Accepted as plan §9.1's rule; flagged for UAT.
2. Every Google Pay completion today settles from the wallet-submit reply (RF-1). The
   fix adds a session query after submission; a slow provider becomes a "still being
   checked" reply rather than a guessed outcome.
3. Split replays: the numbered flow credits "the next pending split". Verifying the
   reference `SPLIT_<split>_TXN_<sale>` against that split means a session opened for an
   earlier share can no longer pay a later one (part of gap 11).

### Missing Steps
A sanitized security event for every mismatch (field name only); route tests that pin the
expected values each flow passes; tests that a failed or mismatched query changes nothing.

### Unsafe Assumptions
That `invoice.amountCents` at completion equals the amount charged for an unsplit invoice.
Session creation charges exactly that value, and an edited invoice amount should not match
the provider's transaction anyway, so a mismatch is the correct outcome.

### Required Ordering Changes
None: T5 uses T1–T4 and needs no migration.

### Open Product / Provider / Legal Questions
Whether a complete session with no transaction means "cancelled" (owner direction).

### Compliance and Data-Handling Notes
Security events and logs carry the mismatched field name and flow only; no session ID,
reference, amount or provider text.

### Test and Rollback Adequacy
Adequate with: verifier unit matrix; query mapping with the real client and a fake
transport; per-flow route tests (expected values passed, unknown and mismatch change
nothing, Google Pay settles from the query, the browser's `result` hint no longer decides
cancelled); full suites. Rollback is a code revert.

### Final Recommendation
**Approve** R2-T5 for the retail token, legacy numbered and invoice checkout completion
paths on `ccr-e07e3100-0wm8kr` from `6f1a67e2`. Tap to Pay (off, R7) and refunds (off, R4)
are out of scope.

| production | `0bc00801…` | 30 | 497 | 111 | 51 | 81 | 26 | 6 |

**Restored snapshot against production: two differences and no others.**

1. **49 columns differ in `position` and in nothing else** — not type, nullability,
   default, collation or identity. Column *sets* are identical. Construction-method
   residue, the same class already recorded between dev and a clean build.
2. **The `public` schema ACL differs, and the restore is the more permissive side.**

   | | owner | `PUBLIC` gets |
   | --- | --- | --- |
   | production | `pg_database_owner` | `U` (usage) |
   | restored snapshot | the restoring role | **`UC` (usage *and create*)** |

   PostgreSQL 15 removed `CREATE` on `public` from `PUBLIC` precisely because it
   lets any role create objects there. Production has the hardened default; the
   restored copy does not. **A restore rehearsed today would come up less locked
   down than the database it replaced.** Nothing in `migrations/` causes this —
   it is a property of how the restore target is created — so it must be fixed
   in the restore procedure, not the history.

   Note the summary counter did not reveal this: `grantsBeyondOwner` reads **1**
   on both sides, because it counts grants rather than comparing their bits. The
   section diff is what found it.

Against the empty build, the restored snapshot differs by exactly the four
accepted differences below.

## Accepted live-fingerprint differences

Recorded rather than repaired, each with its reason:

| # | Difference | Why accepted |
| --- | --- | --- |
| 1 | 5 orphan sequences on live databases | `DROP DEFAULT` leaves the sequence; nothing can consume it once the default is gone, and there is no `DROP SEQUENCE` anywhere in `migrations/`. A clean build already carries two such orphans. |
| 2 | `tapt_stones_merchant_id_idx` absent from live databases | Created by `0010a:20`, which both live databases **baselined** — recorded as applied without executing. The contract now covers it exhaustively, so a future baseline cannot pass while it is missing. |
| 3 | `invoices_rent_requests_token_unique` vs `…_token_key` | Same definition, name only. Drizzle's generated name against Postgres' auto-name. |
| 4 | Neon's 2 `cloud_admin`→`neon_superuser` default privileges | Managed-provider infrastructure. `migrations/` cannot reproduce it and should not try. |

**Consequence, and it is the operative one: digest equality can never gate a
restore or a live comparison.** Differences 1–4 make the digests differ
permanently and correctly. Comparison must be section-by-section. This is why
`verify.yml` gates the *empty-database* fingerprint only, where equality is
achievable and meaningful.

## N/N+1 compatibility

**N+1 against the expanded schema** — the current tree, 98 suites / 1386 tests,
`tsc --noEmit` clean, and all 131 baseline-effect requirements satisfied.

**N against the expanded schema (the rollback direction).** Version N's ORM is
`shared/schema.ts` at `69c3d576`, before either migration. Compared column by
column against the expanded schema's fingerprint: **all 470 columns it declares
still exist with compatible nullability**, and the only disagreement is the
pre-existing `merchant_subscriptions.tier` one that N already had. `0020`'s seven
columns are simply undeclared by N, which is harmless — Drizzle names columns
explicitly in `select()`, and all seven are nullable or defaulted, so an N-shaped
`INSERT` still succeeds. **A code rollback across these migrations is safe.**

The real rollback risk was `0019`: it removes defaults that old code might have
relied on. It did not.

- `platform_fees` and `merchant_settlements` have **no insert site at all** in
  `server/`, so their defaults could never have been consumed.
- `refunds` has one production caller, `routes.ts:5612`, which passes
  `transactionId` and `merchantId` explicitly.
- `transactions` inserts a spread of the caller's object; the live
  `transactions_merchant_id_seq` has never fired.

## What the rogue default actually did, demonstrated

On an isolated database loaded to **200,000 merchants / 200,000 transactions /
200,000 refunds**, with the rogue default injected as the live databases carry it:

**Before `0019`** — an `INSERT` into `refunds` omitting `merchant_id`, for a
transaction belonging to merchant `400002`:

```
inserted refund id=200002  merchant_id=400001
the transaction belongs to merchant 400002, the refund was filed against 400001
```

A refund attributed to the wrong merchant, with **no error**. The foreign key is
only a partial net: it fires when the invented id happens not to exist, and is
silent when it does. Production's merchant ids are low and dense, which is
exactly the silent case.

**After `0019`** — the same insert:

```
inserted refund id=200003  merchant_id=NULL
```

No tenant invented. 200,000 merchant rows unchanged, `crypto_enabled` non-default
on 0 rows.

## Lock and statement budgets

The runner sets a session `lock_timeout` and `statement_timeout` and takes an
advisory lock with its own timeout (`migrate.ts:764-828`, defaults
`advisoryLockMs: 10_000`), restoring the previous values afterwards. Measured on
the 600,000-row database above:

| Migration | Statements | Time |
| --- | ---: | ---: |
| `0019_drop_rogue_fk_defaults.sql` | 7 | **5 ms** |
| `0020_adopt_orphan_columns.sql` | 2 | **5 ms** |

Both are **metadata-only**: `ALTER COLUMN … DROP DEFAULT` touches only the
catalogue, and `ADD COLUMN … DEFAULT <constant>` has been metadata-only since
PostgreSQL 11. Neither rewrites a table, so both are independent of row count and
sit far inside any sane budget. They take `ACCESS EXCLUSIVE` briefly, which is
why the runner's `lock_timeout` matters more than its `statement_timeout` here.

## A tooling defect fixed to get here

`scripts/schema-fingerprint.mjs` refused both restore targets with
`FINGERPRINT_INVALID_CONNECTION`. Its connection allowlist accepted only
`sslmode` and `connect_timeout`, and Neon issues `channel_binding` by default —
a parameter that *hardens* SCRAM against a MITM and can redirect nothing. The
operator would have had to **strip a security parameter** to fingerprint their
own restore target. `channel_binding` is now accepted, with its three valid
values checked and the invalid ones covered by tests.

`RESTORE_REHEARSAL_DATABASE_URL` still fails with `FINGERPRINT_CONNECT_FAILED` —
that Neon branch appears to be gone. `PG16_RESTORE_DATABASE_URL` is live and is
what the convergence above uses.

## What R0-T6A does not close

- **The restore ACL difference is a real open item.** It belongs to the restore
  procedure, not the migration history, and it is recorded here so it is not
  lost. Nobody should treat a rehearsed restore as production-equivalent until
  `PUBLIC` stops getting `CREATE` on `public`.
- **Neither `0019` nor `0020` has been applied to any live database.** They reach
  one through `npm run db:release`, which is a release action.
- **Production row counts remain unread**, by design. "The orphan columns are
  empty" is established for dev only.
- D8 retention is untouched.
